# tee-custody — project definition

*Working name. Rename freely; the Python package is `teecustody`, the npm scope is `@teecustody`.*

**What it is.** A reusable library pair that gives any application an attested, forward-secret channel into a Google Cloud Confidential Space workload, and split-key custody of per-user data so that neither the operator nor the user alone can read it. The backend library runs inside the TEE container; the frontend library runs in the user's web app. A simulator lets both be developed and tested without a TEE.

**What it is not.** Not an application. Not a queue, a database or a KMS. Not a general-purpose crypto library. It has exactly one job: implement `docs/security/tee-security-architecture.md` once, correctly, so host projects never do.

**Normative constraint.** `docs/security/tee-security-architecture.md` (v1.0) governs every design and implementation decision in this repo. See `docs/security/README.md` for how the SDLC roles apply it.

---

## 1. Goals

1. A host project adds this to a Python container and a TypeScript web app and gets the full protocol, custody and recovery flows with no cryptographic code of its own.
2. The host's application logic runs inside the TEE as handlers that see plaintext records but never keys.
3. Everything the host must supply is an interface with a documented contract and at least one provided implementation (GCP adapters for production, simulator adapters for development).
4. A host project's CI can run the entire library test suite against the simulator with no cloud credentials.
5. Mobile clients later, without rewriting the protocol layer: the TypeScript core is platform-agnostic; the web package adds only browser-specific pieces.

## 2. Non-goals for v1

- Mobile share vaults and transports (`@teecustody/mobile` is a later package; the core must not block it).
- Multi-region or multi-cloud attestation. Confidential Space only.
- Host application authentication. The library authenticates a client cryptographically (possession of the client share); mapping a `client_id` to a host user account is a host hook.
- A hosted queue gateway. The repo ships a reference gateway in `examples/`, not a product.

## 4. Package contracts

### 4.1 `teecustody` (Python, inside the TEE)

**Boot and run loop.** One entry point owns the whole lifecycle in §5.1: generate IK, request the attestation token through the launcher socket with the `H(IK_pub)` nonce, generate pre-keys, publish the bundle, refresh on schedule, pull requests, dispatch, respond.

```python
from teecustody import Workload, Config, SessionContext

app = Workload(Config.from_env())        # backends and parameters injected, never discovered

@app.operation("notes.put")
def put_note(ctx: SessionContext, payload: dict) -> dict:
    ctx.records.put(payload["id"], payload["body"].encode())   # DEK minted and wrapped under SK inside
    return {"ok": True}

@app.operation("notes.get")
def get_note(ctx: SessionContext, payload: dict) -> dict:
    return {"body": ctx.records.get(payload["id"]).decode()}

app.run()
```

`SessionContext` exposes `client_id`, `session_id`, `records` (put/get/delete/list over envelope encryption, §7.1) and a `logger` that is already filtered per §11. It never exposes SK, DEKs, shares or session keys. Built-in operations (`enroll`, `open_session`, `close`, `set_trustees`, `release_share`, `recover_start`, `recover_complete`, `rotate_share`, `rotate_sk`) are reserved names the host cannot override.

**Identity.** `client_id` is minted by the library at `enroll` (random, opaque) and returned to the client. From then on a client is whoever presents a valid `cs` for that id. The host maps `client_id` to its own users through the `Directory` backend and a `on_enroll(client_id)` hook. The library never trusts a client-asserted identity for anything but routing.

**Backend interfaces** (each a `Protocol`; the host supplies an implementation or uses a provided one):

| Interface | Contract | Provided implementations |
|---|---|---|
| `Launcher` | Request an attestation token with audience and nonces via the launcher socket | `ConfidentialSpaceLauncher` (production), simulator launcher (same socket, §15.2) |
| `Queue` | Publish bundles; pull requests for this instance; publish responses per client | `PubSubQueue`, `InMemoryQueue` (sim) |
| `KeyWrapper` | Wrap/unwrap the server share with AAD | `KmsKeyWrapper` (Cloud KMS via attested workload identity), `LocalKeyWrapper` (sim only) |
| `ShareStore` | Store/fetch wrapped `ss`, `kcv`, epoch metadata; delete superseded epochs | `FirestoreShareStore`, `InMemoryShareStore` |
| `RecordStore` | Store/fetch ciphertext records with wrapped DEK, nonce, tag, AAD fields | `FirestoreRecordStore`, `GcsRecordStore`, `InMemoryRecordStore` |
| `Directory` | Publish/lookup `IB_pub` and fingerprint per client; host user mapping | `FirestoreDirectory`, `InMemoryDirectory` |
| `TrusteeStore` | Sealed trustee shares and VSS commitments per owner and epoch; pending recoveries and re-sealed shares | `FirestoreTrusteeStore`, `InMemoryTrusteeStore` |
| `Notifier` | Tell trustees a recovery is pending; tell an owner a share was rejected | `LogNotifier` (default), host-provided |

**Modules.**
- `attest`: launcher client, token refresh, nonce encoding.
- `channel`: IK, pre-key batches, bundle signing, HPKE open, session-key export, session AEAD with `seq`, replay cache.
- `custody`: SK lifecycle, Shamir split/combine, `kcv`, envelope encryption, rotation.
- `recovery`: IB keys, Feldman VSS over Ristretto255, sealing to trustees, release, re-seal to RIB, complete, cancel/expire.
- `secrets`: `Secret` wrapper around `bytearray` with explicit `wipe()`, constant-time compare, log filter, `repr` suppression.
- `wire`: canonical CBOR encode/decode against `spec/wire`.
- `backends.gcp`, `backends.memory`.

### 4.2 `teecustody-sim` (Python, development only)

Implements §15 exactly: the launcher socket, the OIDC issuer with discovery and JWKS on loopback, `SIGNERS_REQUIRED` dev signers, `LocalKeyWrapper`, `InMemoryQueue`, and a CLI:

```
teecustody-sim up --image <local image> --audience <aud>      run workload under the simulator
teecustody-sim token [--alter <claim>=<value>|--drop <claim>]  emit a token; the only source of negative vectors
teecustody-sim vectors --out spec/vectors/                    regenerate cross-implementation vectors
teecustody-sim profile --out dev-profile.json                 emit the development trust profile
```

Ships as a separate distribution so it can never be a dependency of `teecustody`.

### 4.3 `@teecustody/core` (TypeScript, platform-agnostic)

No DOM, no `fetch`, no storage. Everything platform-specific enters through interfaces.

```ts
import { TeeClient, TrustProfile, Transport, ShareVault } from "@teecustody/core";

const client = new TeeClient({ trustProfile, transport, vault });
const { clientId } = await client.enroll();                  // first run
const session   = await client.openSession();                // later runs
const res       = await session.request("notes.put", { id, body });
await session.close();

await client.setTrustees([{ clientId: t1, fingerprint: fp1 }, ...], { k: 3 });
await client.releaseShare(recoveryId);                       // as a trustee
const rec = await client.recoverStart();                     // new device
await rec.complete();                                        // once k shares are released
```

**Modules.**
- `attestation`: token parsing, every §6 check as a separate function, driven by a `TrustProfile` object; JWKS fetch via an injected `Fetcher`; pinned-root path for PKI tokens.
- `bundle`: fetch, verify (token, nonce, pre-key signatures, expiry, digest binding), select an unused pre-key.
- `channel`: HPKE seal (Base mode, DHKEM X25519 / HKDF-SHA256 / AES-256-GCM), session-key export, session AEAD with `seq`, request/response framing.
- `custody`: enroll/open-session payloads, epoch and key-id tracking, rotation handling, trustee and recovery flows, fingerprint formatting for out-of-band verification.
- `wire`: canonical CBOR matching `spec/wire`.

**Interfaces the platform package supplies:** `Transport` (post request, poll responses, fetch bundles), `ShareVault` (get/set/clear `cs` under user presence), `Fetcher` (HTTPS GET for JWKS/discovery), `Crypto` (WebCrypto or Node crypto).

### 4.4 `@teecustody/web` (TypeScript, browser)

- `PrfShareVault`: `cs` encrypted under an HKDF of the WebAuthn PRF output, ciphertext in IndexedDB; fails closed if PRF is unavailable (§10.1).
- `FetchTransport`: talks to the reference queue gateway's HTTP contract (`GET /bundles`, `POST /requests/{instance}`, `GET /responses/{client}?after=`); the contract is documented so hosts can implement their own gateway.
- `WebCrypto` adapter.
- `teecustody-profile`: build-time tool that turns `trust-profile.json` into a generated module, and a check that a production bundle contains no development anchors (§13.10). Runs as a build step in the host's pipeline.

### 4.5 `examples/notes-app`

A complete host: a `Workload` with two handlers, a minimal queue gateway (untrusted, relays to Pub/Sub or the in-memory queue), and a web client that enrols, writes a note, closes, reopens and reads it back. It runs under the simulator with one command and under real Confidential Space with documented setup. It is also the integration test.

## 5. Cross-implementation conformance

The Python and TypeScript sides must interoperate byte for byte. `spec/wire` defines every structure in CDDL; `spec/vectors` holds vectors the simulator generates: a bundle, a sealed `open_session`, a session frame in each direction, a wrapped DEK, a share record with `kcv`, a sealed trustee share. Both packages run the same vector suite in CI. A change to the wire format bumps the `proto` string and regenerates the vectors in the same PR.

## 6. Increments

Mapped one-to-one to `framework.yaml` → `increments` (INC-1 … INC-5). Each ends with its acceptance tests green in CI against the simulator, and, from INC-3 on, a smoke run on real Confidential Space.

| # | Scope | Proves |
|---|---|---|
| **INC-1** | Spec in repo, wire schemas, simulator issuer and launcher, Python `attest` module, TS `attestation` module with all §6 checks, negative-vector generation | A token round-trips from simulator to client and every negative vector is rejected (§13.2, §13.9) |
| **INC-2** | Pre-keys, bundles, HPKE open-session, session keys and AEAD framing, replay cache, in-memory queue, `FetchTransport` + reference gateway, `PrfShareVault` | End-to-end encrypted channel in the simulator; protocol tests (§13.3) |
| **INC-3** | `enroll`, `open_session`, SK split 2-of-2, `kcv`, envelope encryption, `RecordStore`, `KmsKeyWrapper`, GCP adapters, `notes-app` example | G1–G3 in the simulator; KMS gating tests on real GCP (§13.4 partial, §13.6) |
| **INC-4** | IB keys, Feldman VSS, `set_trustees`, `release_share`, recovery start/complete/cancel, rotation, `Notifier` | Share and recovery tests (§13.4, §13.5) |
| **INC-5** | Hardened base image, reproducible build, signing tooling, build-separation check, traceability matrix complete, docs, v1.0.0 | §13.1, §13.7, §13.10, §13.11; a host can integrate from the README alone |

## 7. Known risks and open decisions

| # | Risk | Handling |
|---|---|---|
| R1 | No widely audited Feldman VSS library in Python. Ristretto255 group operations are available through libsodium bindings; the VSS layer on top will be small and must be written to test vectors and reviewed as if it were cryptography. | `constraint-deviation` record before INC-4. Only the Python side needs VSS: the client never splits or verifies shares. |
| R2 | WebAuthn PRF availability varies by browser and authenticator. | Fail closed per spec; document the support matrix; this is the main reason mobile comes next. |
| R3 | Confidential Space claim names, launcher socket contract and WIP condition syntax drift. | Verified against current docs in INC-1 and recorded in the PR; the simulator encodes the verified shape, so drift shows up as a simulator conformance failure. |
| R4 | The host image includes the host's handlers, so the digest allow-list is per host, not per library release. | The `teecustody-profile` tool and the README make this explicit; the library cannot ship a digest. |
| R5 | Python cannot zeroise memory reliably. | `secrets` module hygiene plus TEE memory encryption; documented limit, not a blocker. |

Parameters from spec §14 that the host must set: `AUDIENCE`, `TOKEN_TYPE`, digest allow-list, signer keys, `SIGNERS_REQUIRED`, trustee `k`/`n`. Parameters the library fixes with overridable defaults: everything else in the table.
