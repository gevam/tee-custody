# D-02 Development trust profile stores non-canonical loopback literals verbatim

- Severity: Low
- Component: @teecustody/core `attestation/profile.ts` (`parseTrustProfile`, development kind)
- Violates: SR-3 (validation at every trust boundary); SR-1 (profile anchors pinned exactly)
- Found by: QA exploratory, INC-1

## Reproduction
1. Take a valid development profile and set `discovery_url` to `http://0x7f.1/x`.
2. Call `parseTrustProfile(profile)`.

## Expected
Rejected (`INVALID_PROFILE`), or normalised to `http://127.0.0.1/...`. Lookalikes such as
`http://127.0.0.1.evil.test/`, `http://localhost.evil.test/`, userinfo tricks and IPv4-mapped IPv6 are all correctly rejected.

## Actual
Accepted. The WHATWG URL parser resolves `0x7f.1` to `127.0.0.1`, so the check passes, but the raw string is stored
and later handed to the injected `Fetcher`. A fetcher with a different URL parser could resolve the host differently.
The path is also not constrained to the discovery document path (`/x` accepted). Development profiles only; production
profiles are pinned to exact Google URLs and are not affected.

## Suggested direction
Store `url.href`-normalised values, or require the canonical dotted-quad form, and require the well-known discovery path.
