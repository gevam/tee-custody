## Interface contract
API.md §B `wire/types.py` (consumed, final) and `wire/cbor.py`:
```python
def encode(value: CanonicalValue) -> bytes: ...
def decode(data: bytes, limits: DecodeLimits) -> CanonicalValue: ...
```
Normative rules (spec/wire/README.md, T-03), reproduced:
1. RFC 8949 §4.2.1 Core Deterministic Encoding: shortest-form arguments, definite lengths only, map keys in
   bytewise lexicographic order of their encoded form.
2. Permitted: integers in [−2^64, 2^64−1], byte strings, UTF-8 text strings, arrays, maps with text keys only,
   `false`/`true`/`null`. Forbidden: tags, floats, `undefined`, other simple values, indefinite lengths.
3. No duplicate keys; exactly one top-level item; no trailing bytes.
4. Check input length before parsing; scan structure left to right; materialise; re-encode; require byte
   equality. No permissive fallback.
5. `TOO_LARGE` > `max_bytes`; `MALFORMED` truncated / trailing / invalid UTF-8 / additional-info 28–30 /
   additional-info 31 on major type 0, 1, 6 / two-byte simple value < 32 / stray break / empty; `NONCANONICAL`
   non-shortest / indefinite / unsorted / duplicate keys; `UNSUPPORTED_TYPE` tag / float (any value) /
   `undefined` / other simple / non-text key; `LIMIT_EXCEEDED` depth > `max_depth` (top level = 1; every array
   element, map key and map value = container depth + 1) or items > `max_items` (each key and value counts 1). First
   violation in byte order wins; key order and duplicates are evaluated when the map ends.
   Per data-item header the checks run in this order (T-03 rule 5): (a) additional information 28–30 (any major
   type), 31 on major type 0, 1 or 6, or 31 on major type 7 (every break is stray) → `MALFORMED`; (b) argument
   bytes missing, or major type 7 with additional information 24 and argument < 32 → `MALFORMED`; (c) major
   types 0–6 only: non-shortest → `NONCANONICAL`; (d) indefinite → `NONCANONICAL`, tag / float (major type 7,
   additional information 25–27, whatever the value) / `undefined` / other simple / non-text map key →
   `UNSUPPORTED_TYPE`; (e) depth > limit → `LIMIT_EXCEEDED`; (f) array/map: items so far (headers read,
   including this one) + declared children (maps 2 × count, computed without overflow) > limit →
   `LIMIT_EXCEEDED`, then declared children > remaining bytes → `MALFORMED`; strings: declared length > remaining
   bytes → `MALFORMED`, then invalid UTF-8 → `MALFORMED`. Nothing is allocated for a declared length or count
   before (f) passes (ADR 0010 allocation guard).

Implementation decisions (fixed):
- `decode`: (a) `len(data) > limits.max_bytes` → `TOO_LARGE`; (b) an **iterative** (no recursion) structural
  pre-scan over headers enforcing rules 2, 3, 5 including depth/item counts, shortest-form, UTF-8 validity,
  key type, key order and duplicates; (c) only then `cbor2.loads`; (d) `encode(result) == data` else
  `NONCANONICAL`. Any exception other than `WireError` raised in (b)–(d) becomes `WireError(MALFORMED)`.
- `encode`: validate the whole value tree iteratively first (`bool` before `int`; `int` range; `str`, `bytes`,
  `list`, `dict[str, …]` only — `tuple`, `bytearray`, `float`, non-`str` keys → `UNSUPPORTED_TYPE`), then
  `cbor2.dumps(value, canonical=True)`. For text-only keys cbor2's length-first ordering equals rule 1's order;
  vector `map_length_order` proves it.
- `DecodeLimits` fields < 1 → `ValueError("INVALID_LIMITS")` from `decode` before any parsing.
- Depth ceiling (2026-10-01b): module-private `_MAX_DEPTH = 64` in `cbor.py` (not exported; `types.py` is final).
  `decode`: `limits.max_depth > _MAX_DEPTH` → `ValueError("INVALID_LIMITS")`, checked together with the < 1 check,
  before the `TOO_LARGE` check and before any parsing. So `cbor2.loads` and the step-(d) re-encode only ever see
  depth ≤ 64. `encode`: the iterative validation pass also tracks depth (top level 1; list elements and dict
  values = container + 1; keys are `str` and add no nesting). Depth > `_MAX_DEPTH` → `WireError(LIMIT_EXCEEDED)`,
  and `cbor2.dumps` is not called.

## Acceptance criteria (each becomes a test, in this order)
1. Given every `valid` case of `spec/vectors/wire/canonical-cbor.json`, when decoded with the file's limits and
   re-encoded, then the bytes are identical and the Python value has the expected type (`bytes` vs `str`, `dict`, `list`, `None`).
2. Given every `invalid` case, when decoded, then `WireError` with exactly the listed code.
3. Given input of `max_bytes + 1` bytes, when decoded, then `TOO_LARGE` and `cbor2.loads` was never called
   (monkeypatch `teecustody.wire.cbor.cbor2.loads` to fail the test if called).
4. Given `{"b": 1, "aa": 2}`, when encoded, then `a261620162616102`.
5. Given `1.5`, `2**64`, `-(2**64) - 1`, `{1: 2}`, `(1,)`, `bytearray(b"x")`, `{"a": {1.0}}`, when encoded,
   then `UNSUPPORTED_TYPE`; `True` encodes to `f5`, not `01`.
6. Given nesting 10 000 deep (`"81" * 10000 + "00"`) with `max_depth=16`, when decoded, then `LIMIT_EXCEEDED`
   with no `RecursionError`.
7. (hypothesis, ≥ 500 examples) Given any generated `CanonicalValue`, `decode(encode(v), generous_limits)
   == v` and `encode` is deterministic. [2026-10-01b] `generous_limits.max_depth` = 64; the strategy generates
   depth ≤ 64.
8. (hypothesis, ≥ 500 examples) Given arbitrary bytes ≤ 256, `decode` either returns or raises `WireError`;
   nothing else escapes.
9. Given `DecodeLimits(0, 1, 1)`, when decoded, then `ValueError("INVALID_LIMITS")`. [2026-10-01b] Given
   `DecodeLimits(1024, 65, 1024)`, `ValueError("INVALID_LIMITS")` with `cbor2.loads` never called (monkeypatched to
   fail), even for input `00`. Given `max_depth=64`, `00` decodes.
10. Given `9b0000000100000000` (9 bytes declaring 2^32 items) with the vector limits, `LIMIT_EXCEEDED`, and
    `tracemalloc` peak during the call stays below 64 KiB (allocation guard); given `590100`, `MALFORMED`.
    [2026-10-01] The same 64 KiB bound holds for `bb8000000000000000` (`LIMIT_EXCEEDED`) and
    `5bffffffffffffffff` (`MALFORMED`).
11. Given `1b001fffffffffffff`, `1b0020000000000000`, `1bffffffffffffffff`, `3bffffffffffffffff`, they decode to
    2^53−1, 2^53, 2^64−1, −2^64; given `c249010000000000000000`, `UNSUPPORTED_TYPE` (SR-3 integer boundaries).

12. [2026-10-01b] (SR-3, depth ceiling; depth is rule-5 depth, so `0` inside 63 nested lists has depth 64 and
    encodes to `"81" * 63 + "00"`) Given a value of depth 64, `encode` succeeds
    and `decode(…, DecodeLimits(1024, 64, 1024))` round-trips. Both run inside a `threading.Thread` started after
    `threading.stack_size(128 * 1024)` (reset afterwards), so the test proves the ceiling is safe on a small worker
    stack. Given depth 65 (64 nested lists), `encode` → `LIMIT_EXCEEDED`, and decoding `"81" * 64 + "00"` with
    `max_depth=64` → `LIMIT_EXCEEDED`. Given 100 000 deep (built iteratively), `encode` →
    `LIMIT_EXCEEDED` with no `RecursionError`. In both encode-rejection cases `cbor2.dumps` is
    monkeypatched to fail the test if called. This test shows the re-encode path never recurses past the ceiling.
