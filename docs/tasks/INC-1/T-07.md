## Goal
The simulator can mint a production-shaped Confidential Space token signed by a local issuer key, carrying
image signatures from `SIGNERS_REQUIRED` development signers, and can emit any single alteration or any named
negative case in API.md §G — the only source of negative vectors (spec §15.3).

## Interface contract
API.md §C `keys.py`, `token.py` (implements); `constants.py`, `config.py`, `alterations.py`, `cases.py` (consumes).
Spec §15.2 items 2–3 (verbatim): "Signs tokens with a locally generated key using the same JOSE algorithm as the
real service. … The signing key is generated fresh per developer environment and per CI job. It is never
committed and never shared." "`SIGNERS_REQUIRED` development image-signing keys. The simulator signs the local
image digest with them and places the signatures in `submods.container.image_signatures`, so the client's
signature check exercises its normal code path."
Spec §15.3 (verbatim): "The simulator token MUST carry every claim the client verifies (§6) with the same name,
nesting and value type as the real token: `iss`, `aud`, `exp`, `iat`, `eat_nonce`, `hwmodel`, `swname`,
`secboot`, `dbgstat`, `submods.confidential_space.support_attributes`, `submods.container.image_digest`,
`submods.container.image_signatures`, `submods.container.args`, `submods.container.env`." "Default values are
production-shaped so the same checks pass: `swname = CONFIDENTIAL_SPACE`, `secboot = true`, `dbgstat =
disabled-since-boot`, `support_attributes` containing `STABLE`, `image_digest` equal to the actual digest of the
local image, `args` and `env` equal to the actual launch configuration, `eat_nonce` echoing the nonce from the
request, `exp` at `iat + SIM_TOKEN_TTL`." "The values that identify the trust anchor are simulator-specific …
`iss = SIM_ISSUER`, `hwmodel = SIM_HWMODEL`, the token signing key, and the signer keys." "The simulator MUST
offer a claim-alteration mode that emits a token with any single claim changed or removed …"
D-016 (human constraint-deviation): the client counts Google-listed `key_id`s and never verifies signature bytes;
the simulator emulates the attestation service by listing only signatures it verified (T-22). ADR 0009 rules 1, 7
govern JWS framing. Facts: FACTS F-03, F-05, F-06, F-08, F-10, F-11, F-14, F-15 (V-01 record, as amended).

Behaviour (fixed):
- `SimKeys.generate(n)`: `1 ≤ n ≤ MAX_SIGNERS` else `ValueError("INVALID_SIGNERS_REQUIRED")`. Issuer key RSA-2048,
  e=65537; `issuer_kid` = RFC 7638 JWK thumbprint (base64url, no padding). `n` signer keys + 1 `unknown_signer`,
  each RSA-2048, algorithm `DEV_SIGNER_ALGORITHM`, `key_id` per F-11.
- `load_or_create(state_dir, n)`: creates `state_dir` and `state_dir/keys` (0700) when absent; files per API.md
  §C (PEM files 0600); loads existing, generates and writes only missing ones; a key file with wider permissions
  → `ValueError("INSECURE_KEY_FILE")`. [2026-10-01, Orchestrator ruling; API.md §C] `INSECURE_KEY_FILE` covers
  any permission, owner or link problem: a mode that is not owner-only (including write/exec bits), a file
  owned by another user, or a symlink (dangling or not). `ValueError("INVALID_KEY_FILE")` covers content
  problems only: not RSA-2048 with e=65537, an encrypted PEM, or a file that cannot be parsed.
- `issuer_jwks()` = `{"keys": [{"kty":"RSA","alg":"RS256","use":"sig","kid":…,"n":…,"e":…}]}` (base64url, no
  padding), no private members. `sign_jws` = RSASSA-PKCS1-v1_5 SHA-256. `SignerKeyMaterial.sign` = RSA-PSS,
  SHA-256, MGF1-SHA-256, salt length 32.
- `claims(audience, nonces, now)` = `{"iss": issuer, "aud": audience, "iat": now, "nbf": now, "exp": now + ttl_s,
  "eat_nonce": <F-05; omitted when no nonce>, "hwmodel": SIM_HWMODEL, "swname": SWNAME, "secboot": True,
  "dbgstat": DBGSTAT_DISABLED, "submods": {"confidential_space": {"support_attributes": list(SUPPORT_ATTRIBUTES)},
  "container": {"image_reference", "image_digest", "image_signatures": [one per signer, in signer order:
  {"key_id", "signature": base64(sign(image_signature_payload(ref, digest))), "signature_algorithm"}],
  "args": list(args), "env": dict(env)}}}`. Nonces violating F-03 (≤ 6 nonces, each 10–74 bytes) →
  `ValueError("INVALID_NONCE")`. Before an entry is listed the minter verifies its signature over the payload with
  the public key loaded from that signer's `spki_der` (`cryptography`, PSS / MGF1-SHA-256 / salt 32); an entry
  that fails is omitted (Google emulation, T-22). Named cases are applied after this step.
- `frame_jws(header, payload, sign)`: RFC 7515 §5.2 compact serialization over the given octets, base64url
  without padding; `sign` receives the ASCII signing input `b64(header) "." b64(payload)` (ADR 0009 rule 1).
- `mint`: header `{"alg": JWS_ALG, "kid": issuer_kid, "typ": "JWT"}`; JSON = `json.dumps(o, sort_keys=True,
  separators=(",", ":"), ensure_ascii=False).encode()`; framed by `frame_jws` with `keys.sign_jws`. `AlterClaim` sets the value at the path (all parents must exist), `DropClaim`
  removes it (must exist) — otherwise `ValueError("PATH_NOT_FOUND")`; the result is re-signed. `NamedCase`
  applies API.md §G using `token_max_age_s`; unknown id → `ValueError("UNKNOWN_CASE")`.
- `image_signature_payload`: simulator-internal and non-normative (D-016); it returns the UTF-8 of
  `{"critical":{"identity":{"docker-reference":"<R>"},"image":{"docker-manifest-digest":"<D>"},"type":"cosign container image signature"},"optional":null}`
  with D = `image_digest` and R = `image_reference` minus any `@…` suffix and then any `:tag` on the last segment.
  No client reads it. `parse_alteration`: `alter` text `PATH=VALUE` (VALUE parsed with
  `json.loads` if that succeeds, else the literal string); `drop` text `PATH`; PATH segments match
  `^[a-z_][a-z0-9_]*$` joined by `.`; `case` text must be a `NEGATIVE_CASES` id; otherwise
  `ValueError("INVALID_ALTERATION")`.

## Acceptance criteria (each becomes a test, in this order)
1. Given `SimKeys.generate(2)`, two signers + unknown signer with distinct 64-hex `key_id`s equal to SHA-256 of
   their SPKI DER; `issuer_jwks()` has no `d,p,q,dp,dq,qi`; `repr`s contain no PEM or key bytes.
2. Given `load_or_create` twice on one dir, identical keys load; modes are 0700/0600; a 0644 key file raises.
3. Given a minted default token, its header and every claim/type match "Behaviour" and §15.3; the JWS verifies
   with the JWKS key (test uses `cryptography`); each listed `key_id` equals SHA-256 of that signer's SPKI DER and
   its `signature_algorithm` is the signer's algorithm.
3a. (ADR 0009 KAT, sign) Given the RFC 7515 Appendix A.2 private key (loaded into `cryptography` in the test) and
   the A.2 header and payload octets, `frame_jws` reproduces the A.2 compact serialization byte for byte.
3b. (T-22) Given `SignerKeyMaterial.sign` of the second signer monkeypatched to return 256 random bytes, the
   minted token lists only the first signer's entry; with every signer broken, `image_signatures` is `[]`.
4. Given one nonce / two nonces / none, `eat_nonce` is string / array / absent; a 9-byte or 75-byte nonce or 7
   nonces raise `INVALID_NONCE`.
5. Given each §G case id, the decoded token differs from the default exactly as the §G row says (header,
   signature bytes, and the `altered` paths).
6. Given `AlterClaim(("dbgstat",), "enabled")`, `DropClaim(("submods","container","args"))` and each error
   path, the stated result or `ValueError` code.
7. Given `parse_alteration("alter", "secboot=false")`, value is `False`; `"dbgstat=enabled"` → `"enabled"`;
   `"a..b=1"`, `"A=1"`, `("case", "nope")` → `INVALID_ALTERATION`.
8. FACTS F-05, F-06, F-08, F-10, F-11 (algorithm set and `key_id` only) re-confirmed; URL + access date in
   the Task Report.

## Security requirements

- SR-3: every CLI-reachable input (`parse_alteration`, nonces) is validated (criteria 4, 7).
