## Goal
Core turns an untrusted compact JWS into a `ParsedToken` and an untrusted `trust-profile.json` value into a
branded, frozen `TrustProfile`, rejecting anything malformed, unknown or mixing development and production
anchors. These are the two input boundaries every §6 check consumes.

## Interface contract
API.md §D (implements): `parseToken(token: string, maxTokenBytes: number): ParsedToken`,
`parseTrustProfile(input: unknown): TrustProfile`, `encodeIdentityNonce(identityNonce: Bytes): string`,
`identityNonceFromPublicKey(crypto, identityPublicKey): Promise<Bytes>`. Consumes `encoding.ts`, `json.ts`,
`attestation/types.ts` (`brandTrustProfile`, errors). Profile JSON: API.md §E. Derived values: API.md §A.
Spec §15.4 (verbatim): "The client's verification is a single code path parameterized by a **trust profile**:
`{ issuer, jwks_origin | pinned_root, expected_audience, allowed_hwmodels, allowed_digests, signer_keys,
signers_required, expected_args_hash, expected_env_hash }`." "Exactly two profiles exist. **Production:** Google
issuer, Google JWKS or root, production signer keys, production digests. **Development:** `SIM_ISSUER`, the
simulator's loopback JWKS origin or root, development signer keys, local digests. The profile is selected at
build time. There is no runtime switch and no flag that disables any check, in either profile."
Spec §10.2: the trust profile "is compiled into the client at build time and MUST NOT be fetched from the server at runtime."
ARCHITECTURE "Attestation and launcher" (verbatim, 2026-09-30): "Only `parseTrustProfile` creates a profile, and it
rejects unknown keys at every level. `profile_kind` does one thing: it selects which anchor shapes
`parseTrustProfile` accepts." Signer entry: "Each `signer_keys` entry is exactly `{ key_id, algorithm }` … The
profile carries no public-key bytes." ADR 0009 rule 1 (parsing) and rule 9 (development transport) apply.
Facts: FACTS F-06, F-07, F-09, F-11 (V-01 record, as amended).

`parseToken` (all failures `AttestationError("MALFORMED", "token")`; ADR 0009 rule 1): `maxTokenBytes` positive
safe integer; UTF-8 length of `token` ≤ `maxTokenBytes`; exactly three `.`-separated segments; segments 1–2
non-empty, segment 3 may be empty (so `alg_none` is classified by `checkSignature`); segments →
`base64UrlDecode` (strict, canonical) → for 1–2 `utf8DecodeStrict` → `JSON.parse` → must be JSON objects;
`signature = base64UrlDecode(seg3)`; `signingInput = utf8Encode(seg1 + "." + seg2)` — the received ASCII, never
re-serialized. Duplicate JSON members are not detected (ADR 0009 rule 6).

`parseTrustProfile` (failures `TrustProfileError(code, field)`; `field` is the JSON path, `""` for the root):
- Plain object with exactly the 14 §E keys (missing or extra → `INVALID_PROFILE`, field = that key).
- `profile_version === 1`; `profile_kind` ∈ {`production`,`development`}; `token_type === "OIDC"` else
  `UNSUPPORTED_TOKEN_TYPE`.
- Production: `issuer === "https://confidentialcomputing.googleapis.com"`, `discovery_url ===
  "https://confidentialcomputing.googleapis.com/.well-known/openid-configuration"`, `jwks_origin ===
  "https://www.googleapis.com"` (F-07, exact strings); every `allowed_hwmodels` entry ∈ {`GCP_AMD_SEV`,
  `GCP_AMD_SEV_ES`, `GCP_INTEL_TDX`} (F-09 as amended; `GCP_SHIELDED_VM` and `INTEL_TDX` rejected).
- Development: `issuer` is an `https:` URL whose origin ≠ the Google issuer origin; `discovery_url` and
  `jwks_origin` use `http:` or `https:` with hostname `127.0.0.1`, `localhost` or `[::1]`; any other host, under
  either scheme, is rejected (rule 9; amendment 2026-10-01).
- Every URL (`issuer`, `discovery_url`, `jwks_origin`): parses with `URL`, has empty `username`, `password`,
  `search` and `hash`; `jwks_origin` (the only origin field) satisfies `new URL(x).origin === x`.
  `expected_audience`: string, 1–2048 chars. `token_max_age_s`: integer 1–86400. `allowed_hwmodels`,
  `allowed_digests`: non-empty, unique (duplicate reported at its own index); hwmodels non-empty strings;
  digests `^sha256:[0-9a-f]{64}$`.
- `signer_keys`: non-empty array of objects with exactly `key_id` (`^[0-9a-f]{64}$` — lowercase hex of a
  SHA-256 SPKI fingerprint, unique) and `algorithm` (a string not in `SignerAlgorithm` = {`RSASSA_PSS_SHA256`,
  `RSASSA_PKCS1V15_SHA256`, `ECDSA_P256_SHA256`} → `UNSUPPORTED_ALGORITHM`; non-string → `INVALID_PROFILE`).
  An `spki` member is an unknown key → `INVALID_PROFILE` (D-016).
- `signers_required`: integer, 1 ≤ n ≤ `signer_keys.length`. Hashes: `^[0-9a-f]{64}$`.
- Returns `brandTrustProfile(...)`. The source contains no simulator literal (API.md §D note).

`encodeIdentityNonce`: 32 bytes → `hexEncode`; other length → `AttestationError("MALFORMED","nonce")`.
`identityNonceFromPublicKey`: 32-byte key → `crypto.sha256(key)`; other length → same error.

## Acceptance criteria (each becomes a test, in this order)
1. Given a token built with `test/support/jws.ts`, `parseToken` returns header, claims, signature bytes and
   the exact signing input; given the RFC 7515 A.2 token (`test/support/rfc7515.ts`), `signingInput` equals the
   A.2 signing input byte for byte (ADR 0009 KAT).
2. Given each `parseToken` rejection (size + 1 byte, 2 or 4 segments, empty header, `=` padding, non-JSON,
   JSON array payload, invalid UTF-8, a segment with non-zero unused base64url bits, a segment of length ≡ 1
   mod 4), `MALFORMED`/`token`; the error message contains no token text.
3. Given a valid development and a valid production profile object (signer entries with each of the three
   algorithms), `parseTrustProfile` returns a frozen, branded profile.
4. Given each rule above violated one at a time (table-driven), the stated code and field.
5. Given `{..., "skip_verification": true}` (NFR-5), `INVALID_PROFILE` with field `skip_verification`.
6. Given a production profile using a loopback or `http:` discovery/JWKS URL, a `jwks_origin` other than
   `https://www.googleapis.com`, or `hwmodel` `SIMULATED` / `GCP_SHIELDED_VM`, rejected; given a development
   profile with the Google issuer or a non-loopback `http:` URL, rejected; given a URL with userinfo, rejected
   (SR-1 ADR 0009 conditions; SR-7 separation).
6a. Given a signer entry with an `spki` member, a 63-char, 65-char, uppercase or `sha256:`-prefixed `key_id`, or
   algorithm `"ED25519"`, rejected with the stated code (SR-1 D-016 (f), (i) as ruled below).
7. Given 32 bytes `00..1f`, `encodeIdentityNonce` → `"000102…1f"`; given 31 bytes, `MALFORMED`/`nonce`.
8. Given `testCrypto()` and a 32-byte key, `identityNonceFromPublicKey` equals Node's SHA-256 of it.
9. FACTS F-07, F-09 re-confirmed; URL + access date in the Task Report.
