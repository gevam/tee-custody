## Goal
Core proves a token was signed by the issuer the trust profile names, using keys fetched only from the
profile's discovery document and JWKS origin, and that `iss` matches. These two checks gate everything else,
including SR-12 debug-mode reporting (T-15).

## Interface contract
API.md §D: `checkSignature(t: ParsedToken, p: TrustProfile, deps: VerifierDeps): Promise<void>`,
`checkIssuer(t: ParsedToken, p: TrustProfile): void`. Consumes `Fetcher`, `Crypto.verifySignature` [CI-2],
`json.ts`, `encoding.ts`, `AttestationError`.
Spec §6.1 (verbatim): "**Signature.** OIDC token type: verify against the JWKS at the `jwks_uri` obtained from
`https://confidentialcomputing.googleapis.com/.well-known/openid-configuration`, fetched over TLS from that exact
origin. PKI token type: validate the `x5c` chain up to Google's published Confidential Space root and confirm the
root matches a copy embedded in the client. Choose one token type (`TOKEN_TYPE`, §14) and implement only that path."
Spec §6.2 (verbatim): "**Issuer.** `iss` equals `https://confidentialcomputing.googleapis.com`."
Under the development profile the same code uses the profile's `discovery_url`, `jwks_origin` and `issuer`
(spec §15.4: one code path, only the anchors differ). ARCHITECTURE `Fetcher.get`: "returns the HTTP status and
raw response bytes without interpreting JSON … malformed successful discovery/JWKS data is rejected by the Core
as `INVALID_RESPONSE`" — here that surfaces as `UNTRUSTED_SIGNER`. Facts: FACTS F-06, F-07. Only OIDC is
implemented (FACTS scope limits).

`checkSignature` (every failure is `AttestationError(code, "signature")`), ADR 0009 rules 2–5 verbatim in effect:
1. Header, before any fetch, in this order: `alg` absent, not a string, or not exactly `"RS256"` →
   `UNSUPPORTED_ALGORITHM`; any member other than `alg`, `kid`, `typ` (e.g. `crit`, `b64`, `zip`, `enc`, `cty`,
   `jku`, `jwk`, `x5u`, `x5c`, `x5t`, `x5t#S256`) → `UNSUPPORTED_ALGORITHM`; `typ` present and not `"JWT"` →
   `MALFORMED`; `kid` absent, not a string, empty or longer than 256 characters → `UNTRUSTED_SIGNER`;
   zero-length signature → `UNTRUSTED_SIGNER`. No header member is ever used to locate or supply a key.
2. `deps.fetcher.get(p.discovery_url)`: rejection, `status !== 200` (a redirect status included), body >
   `limits.maxDiscoveryBytes`, non-UTF-8, not a JSON object, `issuer !== p.issuer`, or `jwks_uri` not a string
   that parses with `URL`, has empty `username`/`password`, and `new URL(jwks_uri).origin === p.jwks_origin` →
   `UNTRUSTED_SIGNER`. The path may be anything.
3. `deps.fetcher.get(jwks_uri)`: same transport/size (`maxJwksBytes`)/JSON rules; `keys` must be an array;
   candidates = entries with `kid === header.kid` (exact), `kty === "RSA"`, `use` absent or `"sig"`, `alg` absent
   or `"RS256"`, string `n` and `e`. Exactly one candidate, else `UNTRUSTED_SIGNER`. No cache, no refetch.
4. `deps.crypto.verifySignature("RSASSA_PKCS1V15_SHA256", {format: "jwk", jwk: {kty: "RSA", n, e}},
   t.signingInput, t.signature)` with the algorithm as a literal; `false` or any rejection (including
   `INVALID_ARGUMENT` for a modulus < 2048) → `UNTRUSTED_SIGNER`.
Tests build `ParsedToken` values directly from `signJws` output with `encoding.ts`/`JSON.parse`; do not call
`parseToken` (T-10, same wave). Use `mapFetcher(entries, statuses)` for redirect statuses.

`checkIssuer`: `iss` absent → `CLAIM_MISSING`; present but not a string equal to `p.issuer` →
`CLAIM_MISMATCH`; check id `"issuer"`.

## Acceptance criteria (each becomes a test, in this order)
1. Given a token signed by a key published at the profile's JWKS (`test/support/jws.ts`, `mapFetcher`),
   `checkSignature` resolves; the same with a header lacking `typ`.
2. (ADR 0009 KAT) The RFC 7515 A.2 token (`test/support/rfc7515.ts`) has no `kid`, so `checkSignature` rejects it
   `UNTRUSTED_SIGNER` with the fetcher never called. The A.2 verify KAT itself is covered by T-02 criterion 1a
   (adapter) and T-10 criterion 1 (signing input).
3. (Header matrix; the fetcher is never called in any row) `alg` `none`, absent, `42`, `rs256`, `HS256`, `RS384`,
   `RS512`, `PS256`, `ES256` → `UNSUPPORTED_ALGORITHM`; each forbidden member of step 1 → `UNSUPPORTED_ALGORITHM`;
   `typ` `"at+jwt"` / `42` → `MALFORMED`; `kid` absent, `""`, `7`, 257 chars → `UNTRUSTED_SIGNER`; empty
   signature → `UNTRUSTED_SIGNER`.
4. (Algorithm confusion) An HS256 token MACed with the RSA public key (as JWK JSON and as SPKI DER) →
   `UNSUPPORTED_ALGORITHM`. (Embedded key) A token signed by an attacker key carrying it in `jwk`, or pointing to
   it with `jku` → `UNSUPPORTED_ALGORITHM`.
5. (Discovery/JWKS matrix, SR-1) Each → `UNTRUSTED_SIGNER`: discovery `issuer` differs; `jwks_uri` origin
   variants `http://www.googleapis.com`, `https://www.googleapis.com:8443`, `https://u:p@www.googleapis.com`,
   `https://www.googleapis.com.evil.test`; status 302 on either fetch; 500; fetcher rejection; oversize or
   non-JSON document on either fetch; `keys` not an array; candidate filtering (`kty` `EC`, `use` `enc`, `alg`
   `RS384`, missing `n`/`e`, duplicate `kid`); no matching `kid`; a 1024-bit key; same `kid` with a different
   key. A `jwks_uri` on the right origin with a different path still passes.
6. Given one flipped signature bit, `UNTRUSTED_SIGNER`.
7. Given `iss` equal / absent / different / non-string, `checkIssuer` passes / `CLAIM_MISSING` / `CLAIM_MISMATCH` ×2.
8. Given any rejection above, `err.message` equals `signature: <code>` or `issuer: <code>` exactly.
9. FACTS F-06, F-07 re-confirmed; URL + access date in the Task Report.
