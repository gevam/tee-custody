## Goal
Core proves a token was signed by the issuer the trust profile names, using keys fetched only from the
profile's discovery document and JWKS origin, and that `iss` matches. These two checks gate everything else,
including SR-12 debug-mode reporting (T-15).

## Interface contract
API.md §D: `checkSignature(t: ParsedToken, p: TrustProfile, deps: VerifierDeps): Promise<void>`,
`checkIssuer(t: ParsedToken, p: TrustProfile): void`. Consumes `Fetcher`, `Crypto.verifySignature` [CI-2],
`json.ts`, `encoding.ts`, `AttestationError`.
Spec §6.1 (verbatim): "**Signature.** OIDC token type: verify against the JWKS at the `jwks_uri` obtained from
`https://confidentialcomputing.googleapis.com/.well-known/openid-configuration`, fetched over TLS from that exact
origin. PKI token type: validate the `x5c` chain up to Google's published Confidential Space root and confirm the
root matches a copy embedded in the client. Choose one token type (`TOKEN_TYPE`, §14) and implement only that path."
Spec §6.2 (verbatim): "**Issuer.** `iss` equals `https://confidentialcomputing.googleapis.com`."
Under the development profile the same code uses the profile's `discovery_url`, `jwks_origin` and `issuer`
(spec §15.4: one code path, only the anchors differ). ARCHITECTURE `Fetcher.get`: "returns the HTTP status and
raw response bytes without interpreting JSON … malformed successful discovery/JWKS data is rejected by the Core
as `INVALID_RESPONSE`" — here that surfaces as `UNTRUSTED_SIGNER`. Facts: FACTS F-06, F-07. Only OIDC is
implemented (FACTS scope limits).

`checkSignature` (every failure is `AttestationError(code, "signature")`), in this order:
1. `header.alg !== "RS256"` (including `"none"`) or `header.crit` present → `UNSUPPORTED_ALGORITHM`.
   `jku`, `x5u`, `jwk`, `x5c` header members are ignored and never used to select a key.
2. `header.kid` not a non-empty string → `UNTRUSTED_SIGNER`.
3. `deps.fetcher.get(p.discovery_url)`; rejection, `status !== 200`, body > `limits.maxDiscoveryBytes`,
   non-UTF-8, non-JSON-object, `issuer !== p.issuer`, `jwks_uri` not a string whose `new URL(..).origin ===
   p.jwks_origin` → `UNTRUSTED_SIGNER`.
4. `deps.fetcher.get(jwks_uri)`; same transport/size (`maxJwksBytes`)/JSON rules; `keys` must be an array;
   candidates = entries with `kid === header.kid`, `kty === "RSA"`, `use` absent or `"sig"`, `alg` absent or
   `"RS256"`, string `n` and `e`. Exactly one candidate, else `UNTRUSTED_SIGNER`.
5. `deps.crypto.verifySignature("RSASSA_PKCS1V15_SHA256", {format: "jwk", jwk: {kty: "RSA", n, e}},
   t.signingInput, t.signature)`; `false` or rejection → `UNTRUSTED_SIGNER`.
No caching in INC-1: each call fetches. Limits are read from `deps.limits`. Tests build `ParsedToken` values
directly from `signJws` output with `encoding.ts`/`JSON.parse`; do not call `parseToken` (T-10, same wave).

`checkIssuer`: `iss` absent → `CLAIM_MISSING`; present but not a string equal to `p.issuer` →
`CLAIM_MISMATCH`; check id `"issuer"`.

## Acceptance criteria (each becomes a test, in this order)
1. Given a token signed by a key published at the profile's JWKS (`test/support/jws.ts`, `mapFetcher`),
   `checkSignature` resolves.
2. Given `alg` `"none"`, `"HS256"`, `"RS512"`, or `crit: ["x"]`, `UNSUPPORTED_ALGORITHM`, and the fetcher was
   never called.
3. Given a `jku`/`jwk` header pointing at an attacker key that signed the token, `UNTRUSTED_SIGNER`.
4. Given each step-3 and step-4 failure (table-driven: 404 → fetcher rejection, 500 status, oversize, bad JSON,
   wrong discovery `issuer`, `jwks_uri` on another origin, no matching `kid`, two matching keys, `kty: "EC"`,
   `use: "enc"`), `UNTRUSTED_SIGNER`.
5. Given one flipped signature bit, or a valid signature from a different key with the same `kid`,
   `UNTRUSTED_SIGNER`.
6. Given `verifySignature` rejecting with `CapabilityError("INVALID_ARGUMENT")`, `UNTRUSTED_SIGNER`.
7. Given `iss` equal / absent / different / non-string, `checkIssuer` passes / `CLAIM_MISSING` / `CLAIM_MISMATCH` ×2.
8. Given any rejection above, `err.message` equals `signature: <code>` or `issuer: <code>` exactly.
9. FACTS F-06, F-07 re-confirmed; URL + access date in the Task Report.
