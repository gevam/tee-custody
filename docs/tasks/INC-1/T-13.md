# T-13: Implement the §6.8 image check (digest allow-list and independent image-signature verification)

## Goal
Core itself verifies that the attested image digest is allow-listed and carries valid signatures from at least
`signers_required` distinct signer keys embedded in the trust profile — never relying on server enforcement.

## Interface contract
API.md §D (implements): `imageSignaturePayload(imageReference: string, imageDigest: string): Bytes`,
`checkImage(t: ParsedToken, p: TrustProfile, e: ExpectedAttestation, deps: VerifierDeps): Promise<readonly
string[]>`. Consumes `Crypto.verifySignature` [CI-2], `json.ts`, `encoding.ts` (`base64Decode`, `utf8Encode`),
`AttestationError`. Facts: FACTS F-08, F-11, F-12 (payload format and the ECDSA scope limit).
Spec §6.8 (verbatim): "**Image.** `submods.container.image_digest` is on the allow-list embedded in the client at
build time, and `submods.container.image_signatures` contains valid signatures from at least `SIGNERS_REQUIRED`
of the signer public keys embedded in the client. The client enforces this independently. "The server enforces
it" is not an acceptable reason to skip it."
ARCHITECTURE: "`ExpectedAttestation` contains the expected identity nonce and workload digest."

`imageSignaturePayload`: exactly FACTS F-12 — strip an `@…` suffix from `imageReference`, then strip a `:tag`
suffix only if the `:` is after the last `/`; build the JSON text with that key order and no whitespace; JSON
string escaping as `JSON.stringify` does for the two string values; return UTF-8 bytes.

`checkImage` (check id `"image"`), in order:
1. `submods.container.image_digest` absent → `CLAIM_MISSING`; not a string in `p.allowed_digests` →
   `CLAIM_MISMATCH`; `e.imageDigest !== undefined` and different → `CLAIM_MISMATCH`.
2. `submods.container.image_reference` absent → `CLAIM_MISSING`; not a non-empty string → `CLAIM_MISMATCH`.
3. `submods.container.image_signatures` absent → `CLAIM_MISSING`; not an array → `CLAIM_MISMATCH`; more than 64
   entries → `CLAIM_MISMATCH`.
4. For each entry: skip it unless it is an object with string `key_id`, `signature`, `signature_algorithm`;
   find the profile signer with equal `key_id`; skip unless `signature_algorithm === signer.algorithm`; decode
   `signature` with `base64Decode` (skip on `EncodingError`); `deps.crypto.verifySignature(signer.algorithm,
   {format: "spki", der: signer.spki}, payload, sig)` — count the `key_id` once if `true`; skip on `false` or
   rejection.
5. Distinct verified `key_id`s < `p.signers_required` → `UNTRUSTED_SIGNER`. Otherwise return them sorted ascending.

## Acceptance criteria (each becomes a test, in this order)
1. Given `("us-docker.pkg.dev/p/r/img:v1@sha256:ab…", "sha256:ab…")`, `("localhost:5000/img:dev", …)` and
   `("img", …)`, `imageSignaturePayload` yields references `us-docker.pkg.dev/p/r/img`, `localhost:5000/img`,
   `img` in the exact F-12 bytes.
2. Given two profile signers (`signers_required` 2) and a token signed by both (`test/support/jws.ts`
   `signPayload`, PSS and PKCS1 each once), `checkImage` resolves to both `key_id`s sorted.
3. Given each step-1 to step-3 failure, the stated code.
4. Given only one valid signature, the same signer twice, a signature by an unknown key, a signature with one
   flipped bit, a `signature_algorithm` differing from the profile key's, an invalid-base64 signature, or a
   malformed entry (each with `signers_required` 2), `UNTRUSTED_SIGNER`.
5. Given three valid signatures, one unknown and one malformed entry with `signers_required` 2, resolves to the
   three valid `key_id`s (extra entries are ignored, not fatal).
6. Given `verifySignature` rejecting for one entry, that entry is skipped, not fatal.
7. Given any failure, `err.message` is exactly `image: <code>`.
8. FACTS F-11, F-12 re-confirmed; URL + access date in the Task Report.
