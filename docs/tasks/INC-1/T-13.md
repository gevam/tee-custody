## Goal
Core itself requires that the attested image digest is allow-listed and that the Google-signed token names at
least `signers_required` distinct signers embedded in the client's trust profile, each with the algorithm the
profile expects. It never relies on server enforcement, and it never re-verifies signature bytes (D-016).

## Interface contract
API.md §D (implements): `checkImage(t: ParsedToken, p: TrustProfile): readonly string[]` — synchronous; no
crypto, no fetch. Consumes `json.ts` (`getPath`, `isJsonObject`), `AttestationError`, `SignerKey`
(`{key_id, algorithm}`). Facts: FACTS F-08, F-11, F-12, F-16 (V-01 record, as amended).
Spec §6.8 (verbatim): "**Image.** `submods.container.image_digest` is on the allow-list embedded in the client at
build time, and `submods.container.image_signatures` contains valid signatures from at least `SIGNERS_REQUIRED`
of the signer public keys embedded in the client. The client enforces this independently. "The server enforces
it" is not an acceptable reason to skip it."
D-016 (human, verbatim decision): "Client requires ≥ `SIGNERS_REQUIRED` distinct `key_id`s in the Google-signed
token equal to SHA-256(SPKI DER) fingerprints of embedded signer keys, with `signature_algorithm` in the allowed
set (the check Google's documented WIP policy uses)."
ARCHITECTURE "Image check" (verbatim steps): "1. `submods.container.image_digest`: absent → `CLAIM_MISSING`; not
a string in `allowed_digests` (exact match) → `CLAIM_MISMATCH`. 2. `submods.container.image_signatures`: absent →
`CLAIM_MISSING`; not an array → `CLAIM_MISMATCH`. 3. An entry **counts** only if all of the following hold: it is
an object; its `key_id` is a string exactly equal (case-sensitive) to a profile `key_id`; its
`signature_algorithm` is a string equal to that profile entry's `algorithm`; its `signature` is a non-empty
string. Entries that do not count are ignored: unknown signers, malformed entries and algorithm mismatches.
Duplicate `key_id`s count once. 4. Fewer than `signers_required` distinct counted `key_id`s →
`UNTRUSTED_SIGNER`. 5. Otherwise, return the distinct counted `key_id`s sorted ascending. … The `signature` bytes
are not decoded or verified by the client (D-016)."
Every failure is `AttestationError(code, "image")`. `image_reference` is not read.

## Acceptance criteria (each becomes a test, in this order; `image_digest` allow-listed unless stated)
1. (a) Given `signers_required` 2 and entries for both profile signers, returns both `key_id`s sorted.
2. (b) Given one matching entry only, `UNTRUSTED_SIGNER`.
3. (c) Given the same matching `key_id` repeated twice (and `signers_required` 2), `UNTRUSTED_SIGNER`.
4. (d) Given two matching entries plus unknown `key_id`s, returns only the two; given one matching plus one
   unknown, `UNTRUSTED_SIGNER`.
5. (e) Given a matching `key_id` whose `signature_algorithm` differs from the profile entry's `algorithm`, or is
   `"ED25519"`, that entry does not count.
6. (f) Given the `key_id` in uppercase hex, 63 or 65 characters, or prefixed `sha256:`, it does not match.
7. (g) Given entries with a missing or non-string `key_id`, `signature` or `signature_algorithm`, an empty
   `signature`, or a non-object entry, they are skipped (not fatal).
8. (h) Given `image_signatures` absent → `CLAIM_MISSING`; `{}` or `"x"` → `CLAIM_MISMATCH`.
9. Given `image_digest` absent → `CLAIM_MISSING`; not allow-listed, uppercase, or a number → `CLAIM_MISMATCH`
   (evaluated before signatures).
10. Given a `signature` that is not valid base64, the entry still counts (bytes are never decoded, D-016).
11. Given `checkImage` called, it returns synchronously (not a `Promise`); SR-1: the client never calls
    `verifySignature` for image signatures (the test scans `image.ts` source for `verifySignature` and `crypto`).
12. Given any failure, `err.message` is exactly `image: <code>`.
13. FACTS F-11 (algorithm set, `key_id` definition) re-confirmed; F-16 status noted; URL + access date in the
    Task Report.
