## Goal
`verifyAttestation` is the single code path a client uses to trust a token: it runs every spec §6 check in a
fixed order, rejects on the first failure, returns a `VerifiedAttestation` only on full success, and reports a
debug-mode token to the injected `SecurityEventSink` only after signature and issuer have passed.

## Interface contract
API.md §D (implements): `launchConfigHash`, `checkLaunchConfig`, and [CI-1]
`verifyAttestation(token, profile, expected, events, deps): Promise<VerifiedAttestation>`. Consumes
`parseToken` (T-10), `checkSignature`/`checkIssuer` (T-11), `checkAudience`/`checkTime`/`checkNonce`/
`checkPlatform`/`isDebugMode`/`checkSupportAttributes` (T-12), `checkImage` (T-13, sync), `encodeCanonical` (T-09),
`isBrandedTrustProfile`/`createVerifiedAttestation`, `SecurityEventSink`, `SecurityEvent`.
Spec §6 preamble (verbatim): "The client MUST perform every check below on every bundle before using any key
from it. Failure of any single check is fatal for that bundle. The checks are one code path, parameterized by the
trust profile compiled into the build (§15.4); the logic never varies between builds, only the trust anchors."
Spec §6.9 (verbatim): "**Launch configuration.** `submods.container.args` and `submods.container.env` match the
expected values or the expected hash. An image can be neutered by its launch arguments; the token exposes them so
the client can check."
ARCHITECTURE verifier contract (verbatim): "`events` is required, not optional. … Once the signature check (§6.1)
and the issuer check (§6.2) have both passed under `profile`, Core calls `events.report({ code:
"ATTESTATION_DEBUG_MODE", at })` exactly once for that call if `dbgstat` is present and differs from the required
value. This happens whatever the outcome of the other checks. Core does not await the report for the verification
decision, and it catches and discards a rejected report. The token is still rejected with `CLAIM_MISMATCH`; the
error contract below is unchanged. A token that fails signature or issuer verification never triggers a report,
so forged tokens cannot raise alerts. The event carries no token content, claims, instance ID or key material."
"… Any failed/missing check rejects the whole token. There is no verification bypass."

`launchConfigHash(v, crypto)`: lowercase hex of `crypto.sha256(encodeCanonical(v))` (API.md §A).
`checkLaunchConfig` ("launch_config"): `args` absent → `CLAIM_MISSING`; not an array of strings → `CLAIM_MISMATCH`;
hash ≠ `p.expected_args_hash` → `CLAIM_MISMATCH`; then `env` the same with a JSON object whose values are all
strings, converted to `Map` (key order irrelevant — the encoder sorts), vs `p.expected_env_hash`.

`verifyAttestation` order: (0) `!isBrandedTrustProfile(profile)` → `MALFORMED`/`profile`; (1) `parseToken(token,
deps.limits.maxTokenBytes)`; (2) `checkSignature`; (3) `checkIssuer`; (4) if `isDebugMode(t)`: build
`{ code: "ATTESTATION_DEBUG_MODE", at: deps.now() }` and call `events.report` inside `try`; attach a no-op
rejection handler; never await it; a synchronous throw is swallowed; (5) `checkAudience`; (6) `checkTime(t,
profile, deps.now())`; (7) `checkNonce`; (8) `checkPlatform`; (9) `checkSupportAttributes`; (10) `signerKeyIds = checkImage(t, profile)` (synchronous, D-016);
(11) `checkLaunchConfig`; (12) return `createVerifiedAttestation({ issuer, audience, imageDigest, signerKeyIds,
hwmodel, issuedAtMs: iat * 1000, expiresAtMs: exp * 1000 })`. Any non-`AttestationError` thrown in step k becomes
`AttestationError("MALFORMED", <check id of step k>)`.

## Acceptance criteria (each becomes a test, in this order)
1. Given `args ["/app/workload"]`, `launchConfigHash` equals hex SHA-256 of `81 6d "/app/workload"`; given env
   `{"B":"2","A":"1"}` and `{"A":"1","B":"2"}`, the hashes are equal.
2. Given `args`/`env` matching / absent / wrong type / non-string value / altered, `checkLaunchConfig` passes /
   `CLAIM_MISSING` / `CLAIM_MISMATCH` ×3.
3. Given a fully valid token (built with `test/support/jws.ts`), `verifyAttestation` returns a frozen result with
   the documented fields, `signerKeyIds` sorted, and `events.report` never called.
4. Given a token failing exactly one check (one case per step 1–11, table-driven), it rejects with that step's
   code and check id.
5. Given `dbgstat: "enabled"` and valid signature/issuer, it rejects `CLAIM_MISMATCH`/`platform` and
   `report` was called exactly once with an object whose only keys are `code` and `at`, `at === deps.now()`.
6. Given `dbgstat: "enabled"` plus an invalid signature, or plus a wrong `iss`, `report` is never called.
7. Given `dbgstat: "enabled"` plus a wrong audience, `report` is called once and the error is `audience`.
8. Given a sink whose `report` returns a never-settling promise, a rejecting promise, or throws synchronously,
   the verification result is identical to criterion 5 and no unhandled rejection is raised.
9. Given a plain object shaped like a `TrustProfile` (not from `parseTrustProfile`), `MALFORMED`/`profile`.
10. Given every rejection above, `err.message` contains no substring of the token.

## Security requirements

- SR-1 / NFR-5: criteria 3–4, 9 — one fixed path, no bypass, profile provenance enforced.
- SR-3 / SR-11: criteria 2, 10.
