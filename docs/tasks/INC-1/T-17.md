## Goal
The simulator produces (a) the development trust profile a client build embeds and (b) one canonical-CBOR
vector suite holding the positive token, every §G negative case, the development profile, a production-shaped
fixture profile and the HTTP bodies a test Fetcher serves — so Python and TypeScript are tested against the
same bytes and the simulator's alteration mode is the only source of negative vectors.

- `packages/teecustody-sim/src/teecustody_sim/profile.py`, `vectors.py` (replace stub bodies)
- `packages/teecustody-sim/tests/test_profile.py`, `packages/teecustody-sim/tests/test_vectors.py`,

## Interface contract
API.md §C `profile.py`, `vectors.py` (implements); §A (hashes), §E (profile JSON), §F, §G (cases);
`spec/wire/attestation-vectors.cddl` (T-03, schema); consumes `teecustody.wire.encode` (T-04), `SimKeys`,
`TokenMinter` (T-07), `NEGATIVE_CASES`, constants. Facts: FACTS F-07, F-09.
Spec §15.3 (verbatim): "This is the only source of negative vectors for §13.2." §13.9 (verbatim): "A simulator
token with default values passes every §6 check under the development profile. The same token fails the issuer
and signature checks under the production profile. Every negative vector in item 2 is produced by the
simulator's claim-alteration mode (§15.3), so the test suite and the simulator cannot drift apart."
§15.4: "**Development:** `SIM_ISSUER`, the simulator's loopback JWKS origin or root, development signer keys,
local digests." §15.5: "Production client builds MUST NOT contain the development profile, `SIM_ISSUER`, the
simulator root or JWKS, or the development signer keys."

Behaviour (fixed):
- `launch_config_hashes(args, env)` → `(hex(sha256(encode(list(args)))), hex(sha256(encode(dict(env)))))`.
- `build_trust_profile(...)` → the §E dict: `profile_version` 1, `profile_kind` `"development"`, `token_type`
  `"OIDC"`, `issuer` `SIM_ISSUER`, given `discovery_url`/`jwks_origin`/`expected_audience`/`token_max_age_s`,
  `allowed_hwmodels` `[SIM_HWMODEL]`, `allowed_digests` `[launch.image_digest]`, `signer_keys` one entry per
  signer `{key_id: sha256(signer.spki_der).hexdigest(), algorithm: signer.algorithm}` — `key_id` is computed
  from the SPKI DER, never copied from `signer.key_id` (ARCHITECTURE "Image check"; D-016) — `signers_required`,
  the two hashes.
  `signers_required > len(signers)` → `ValueError("INVALID_SIGNERS_REQUIRED")`.
- Signer normalisation (amendment 2026-10-01), applied in `build_trust_profile` before any entry is emitted, in
  signer order: `canonical = load_der_public_key(spki_der).public_bytes(Encoding.DER,
  PublicFormat.SubjectPublicKeyInfo)` (`cryptography`). Load failure, or `canonical != spki_der`, →
  `ValueError("NONCANONICAL_SIGNER_SPKI")` (an emitted `key_id` must equal the one T-07 puts in tokens, which is
  SHA-256 of `spki_der`; re-encoding silently would make them diverge). Two signers whose `canonical` bytes are
  equal → `ValueError("DUPLICATE_SIGNER_KEY")`. So each key appears once, in one encoding, and `key_id` is
  SHA-256 of that canonical DER. Checks run in that order; `INVALID_SIGNERS_REQUIRED` is checked last.
- `generate_suite(out_dir, now=None)`: `now = int(time.time())` if None. Fresh `SimKeys.generate(2)` (never
  the state dir). Fixed launch: `LaunchConfig("localhost/teecustody-vectors:1", "sha256:" +
  sha256(b"teecustody-sim vector image").hexdigest(), ("/app/workload",), (("PYTHONUNBUFFERED", "1"),))`.
  Fresh Ed25519 identity key; nonce = lowercase hex SHA-256 of its raw public key. Audience
  `https://vectors.teecustody.test/tee`. Discovery `http://127.0.0.1:8791/.well-known/openid-configuration`,
  JWKS origin `http://127.0.0.1:8791`, JWKS URL `http://127.0.0.1:8791/jwks`; the `http` map holds the
  discovery document `{"claims_supported": ["aud","dbgstat","eat_nonce","exp","hwmodel","iat","iss","nbf",
  "secboot","submods","swname"], "id_token_signing_alg_values_supported": ["RS256"], "issuer": SIM_ISSUER,
  "jwks_uri": "http://127.0.0.1:8791/jwks", "response_types_supported": ["id_token"], "scopes_supported":
  ["openid"], "subject_types_supported": ["public"]}` (same content T-08's `IssuerServer` serves) and
  `keys.issuer_jwks()`, each as `json.dumps(o, sort_keys=True, separators=(",", ":")).encode()`. The
  production fixture profile: Google issuer and discovery URL (F-07), `jwks_origin` `https://www.googleapis.com`,
  `allowed_hwmodels` `["GCP_AMD_SEV", "GCP_AMD_SEV_ES", "GCP_INTEL_TDX"]` (F-09 as amended), `allowed_digests`
  [the fixed digest], two fixture `{key_id, algorithm}` entries computed from a second `SimKeys.generate(2)`,
  same audience and hashes; `http` also maps the Google discovery URL to `{"issuer":
  "https://confidentialcomputing.googleapis.com", "jwks_uri": "https://www.googleapis.com/service_accounts/v1/metadata/jwk/signer@confidentialspace-sign.iam.gserviceaccount.com"}`
  (F-07) and that `jwks_uri` to a JWKS holding one fixture RSA-2048 key with `kid` `"production-fixture"`,
  `alg` `RS256`, `use` `sig`. Cases: `valid` + every `NEGATIVE_CASES` row in order, each minted
  by `TokenMinter(...).mint(audience, [nonce], now, NamedCase(id))` (`valid` with no alteration), with
  `expect`/`check`/`error_code`/`altered`/`debug_event` from the row (`"none"` for `valid`). Top-level fields per
  the CDDL, `verify_at_ms = now * 1000`. Write `encode(suite)` to `out_dir/attestation/suite.cbor`
  (directories created), return that path.
- `generate_corpus(out_dir, seed=1, count=512)` (ADR 0010 differential corpus): `count < 500` →
  `ValueError("INVALID_COUNT")`. `rng = random.Random(seed)`. For `i` in `range(count)`: build a random
  `CanonicalValue` (depth ≤ 4, ≤ 8 items per container, ints drawn from edge values {0, 23, 24, 255, 256, 65535,
  65536, 2^32−1, 2^32, 2^53−1, 2^53, 2^64−1, −1, −24, −25, −2^64} and uniform, short bytes and text including
  non-ASCII), `b = encode(v)`, apply one mutation chosen by `rng` (flip one bit; insert one random byte; delete one
  byte; truncate at a random position; replace the first byte with a random byte), and record
  `{"id": f"m{i:04d}", "hex": b.hex(), "outcome": "accept" or the WireError code}` from `decode(b, limits)` with
  limits `{max_bytes 1024, max_depth 8, max_items 256}`. Write the API.md §F JSON (`json.dumps(indent=None,
  sort_keys=True, separators=(",", ":"))`) to `out_dir/wire/differential-corpus.json`; return that path.

## Acceptance criteria (each becomes a test, in this order)
1. Given args `["/app/workload"]` and env `[("PYTHONUNBUFFERED","1")]`, the hashes are
   `0d7b8d1aa29f148b5f78df8a6214175db1991281625e7727ce2ca5945f090c99` (SHA-256 of `816d2f6170702f776f726b6c6f6164`)
   and `942fabd2e68b234f374ade89d81e9adf3414e9603216bb66b8252ceff35f3ecb` (SHA-256 of
   `a170505954484f4e554e42554646455245446131`).
2. Given keys and a launch config, `build_trust_profile` has exactly §E keys and values; each signer entry has
   exactly `key_id`, `algorithm`, with `key_id == sha256(spki_der).hexdigest()` even when `signer.key_id` is
   monkeypatched to a wrong value (computed, not copied; SR-1 (i)); `signers_required` 3 with 2 signers raises.
2a. Given signers where one has its SPKI re-encoded (RSA key wrapped as an `id-RSASSA-PSS` SPKI built in the
   test with `cryptography`/DER bytes, or any non-canonical DER of the same key), `NONCANONICAL_SIGNER_SPKI`;
   given the same `SignerKeyMaterial` twice, or two objects with equal key material, `DUPLICATE_SIGNER_KEY`
   even with `signers_required` 1; given `SimKeys.generate(2)` signers, no error and two distinct `key_id`s.
3. Given `generate_suite(tmp, now=1_900_000_000)`, the file decodes with `teecustody.wire.decode`, re-encodes to
   identical bytes, and has exactly the CDDL keys and constants.
4. Given the suite, case ids and metadata equal `NEGATIVE_CASES` (plus `valid` first); every token's JWS
   signature verifies with the suite's JWKS key except `alg_none`, `token_signature_corrupted` and
   `debug_bad_signature`.
5. Given the suite's `profile_json`, `json.loads` yields a dict equal to `build_trust_profile` for the suite's
   keys and launch; `production_profile_json` has `profile_kind` `production` and no `SIM_ISSUER`, loopback URL
   or development signer `key_id`.
6. Given two runs, the files differ (fresh keys) but have identical structure and case metadata.
7. Given the suite bytes, they contain no `PRIVATE KEY` text and no private JWK member (`"d"`, `"p"`, `"q"`).
7a. Given `generate_corpus(tmp)` twice with seed 1, the files are byte-identical; it has ≥ 500 cases, unique ids,
   at least one case per `WireErrorCode` except `TOO_LARGE` and at least 50 `accept` cases (tune the value
   generator, not the check); `count=499` raises `INVALID_COUNT`; re-decoding each case reproduces its outcome.
8. FACTS F-07, F-09 re-confirmed; URL + access date in the Task Report.
