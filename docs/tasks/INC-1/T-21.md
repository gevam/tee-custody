## Goal
`Simulator.start()` turns every operating-system failure it can predict into a stable `SimConfigError` code, so
it never surfaces as `INTERNAL`. It rejects launch-environment names the container runtime cannot carry. Under a
100-connection burst the launcher socket gives every client either an answer or an explicit 503; no client
fails at `connect()`.

## Interface contract
API.md §C `Simulator`, `SimConfigError`, `SimLimits` are unchanged except for the new code. API.md §C addition:
"`BIND_FAILED`: the issuer could not bind `issuer_host:issuer_port` (address not local, port in use, or not
permitted)."

Behaviour (fixed):
1. **`_validate` additions** (run before anything is created, in the existing order):
   - In the `INVALID_LAUNCH_CONFIG` group: a `launch.env` name that is empty or contains `=` or `\0`, or a value
     containing `\0` → `INVALID_LAUNCH_CONFIG` (D-04).
   - In the `INVALID_PATH` group: `os.path.lexists(socket_path)` → `INVALID_PATH`, whatever the entry is
     (regular file, directory, symlink, stale or live socket). A clean `stop()` already unlinks the socket.
2. **`_serve` mapping.** Each step's `OSError` (any subclass) becomes `raise SimConfigError(code) from None`:
   - `SimKeys.load_or_create` → `INVALID_PATH` (its `ValueError` codes are unchanged);
   - `IssuerServer.start()` → `BIND_FAILED`;
   - `LauncherServer.start()` → `INVALID_PATH`;
   - each `_write_file` → `INVALID_PATH`.

   `start()`'s existing `stop()`-on-failure still runs. Exception text and logs carry the code only.
3. **Listen backlog.** `_BoundedServer.request_queue_size = 128`, which covers both servers.
4. **Launcher busy reply.** `_BoundedServer` gains the class attribute `busy_reply: bytes | None = None`.
   - The launcher's server class sets it to the exact bytes
     `b"HTTP/1.0 503 Service Unavailable\r\nContent-Type: text/plain\r\nContent-Length: 19\r\nConnection: close\r\n\r\nSERVICE_UNAVAILABLE"`.
   - In `process_request`'s "no slot and no overflow slot" branch, if `busy_reply` is set, call
     `request.send(busy_reply, socket.MSG_DONTWAIT)` and ignore any `OSError`, then `shutdown_request` as now.
     No thread is started and nothing is read.
   - The issuer keeps `None`, so its behaviour is unchanged (a TCP close with unread data would race a reset).

## Acceptance criteria (each becomes a test, in this order)
1. Given `launch.env` with name `""`, `"A=B"`, `"A\0"`, or value `"x\0"`, `start()` raises
   `INVALID_LAUNCH_CONFIG` and creates no file or socket.
2. Given a regular file, a directory, a dangling symlink, a symlink to a socket, a stale socket file or a live
   bound socket at `socket_path`, `start()` raises `INVALID_PATH`. The entry is left untouched (same inode, same
   contents) and no key, state or token file is created.
3. Given `issuer_host="192.0.2.1"` with `allow_non_loopback=True` (TEST-NET-1, not local, so EADDRNOTAVAIL), or
   `issuer_port` held by another bound socket on 127.0.0.1, `start()` raises `BIND_FAILED`. No launcher socket
   or state file remains.
4. Given `SimKeys.load_or_create`, `LauncherServer.start` and `_write_file` each monkeypatched to raise
   `PermissionError` (one test per site), `start()` raises `INVALID_PATH`. `str(err)` is the code only, both
   servers are stopped and the socket path does not exist. Given a non-`OSError` (`RuntimeError`) at the same
   sites, it propagates unchanged.
5. `test_api_surface.py` pins `SimConfigErrorCode` with `BIND_FAILED` appended. This is the first red test.
6. (D-03, deterministic) Setup: a `LauncherServer` with default `SimLimits` (8 slots) and a `mint` that blocks
   on an `Event`. Each of 100 threads does `settimeout(10)`, `connect()`, then `sendall` of a valid request
   (ignoring `BrokenPipeError`/`ConnectionResetError`), then reads to EOF. Then:
   - Every `connect()` succeeds. On trunk, backlog 5 gives `BlockingIOError` here.
   - After 92 clients have each received a complete `503 SERVICE_UNAVAILABLE` response, the test sets the event.
   - The remaining 8 receive `200` with the minted text.
   - Totals are exactly 8 × 200 and 92 × 503. No client sees EOF without a status line.
7. `_IssuerHTTPServer.request_queue_size == 128`. The existing issuer flood and 503 tests pass unchanged.
