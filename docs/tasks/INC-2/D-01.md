## Rulings (T-31 A4)
- None of these is a harness, client or server defect. INC-2 lets a session pipeline up to `maxInFlight` 8
  (INC-2-API §7.4), but it does not promise in-order arrival or that every pipelined request succeeds. §15 Q8
  defers ordering to INC-3 (B-26). FR-4/FR-5 require only a round trip and the rejection of invalid or replayed
  frames.
- 429 is the gateway's contracted back-pressure. The harness keeps the default `GatewayLimits` (A4).
- The behaviour behind F4 is contracted (INC-2-API §4.13, §4.10 step 2; spec §5: the client times out).

## Required fix (each item is a test change; keep every other assertion)
1. **F3.** `FAST_LIMITS.pollIntervalMs` = `DEFAULT_CHANNEL_LIMITS.pollIntervalMs` (500). Keep `responseTimeoutMs`
   20 000.
2. **F1.** Keep: nine calls started synchronously; the 9th rejects `INVALID_ARGUMENT`. Change: use
   `{ ...FAST_LIMITS, responseTimeoutMs: 3000 }` for this session. Each of the first eight either fulfils with
   `get("n") === i`, or rejects with `ChannelError` `TIMEOUT` (Q8), or `TRANSPORT`/`UNAVAILABLE` (§6
   per-source in-flight cap). At least one fulfils (the first frame to arrive is always accepted). Then
   `session.request("test.echo", echo(99))` fulfils with `n === 99`.
3. **F2/F2b.** Use `{ ...FAST_LIMITS, responseTimeoutMs: 3000 }`.
   - A rejected burst item may be `TRANSPORT`/`UNAVAILABLE` or `TIMEOUT`.
   - Run each host retry under `Promise.allSettled` and accept the same two outcomes.
   - Keep the nonce assertions and `seen.size >= 24` unchanged.
4. **F4.** In `e2e-support.ts`, `clientParts` wraps the base `FetchTransport` in a module-level pre-key ledger.
   This stands in for the persistent used set of a host with one client.
   - `postRequest`: if the envelope's `kind` is `"open"`, decode its `aad` (public wire format, `decodeCanonical`)
     and record `(instance_id, prekey_id)`.
   - `listBundles`: re-encode each bundle with the recorded pre-key ids removed from `prekeys`. Use
     `encodeCanonical`, as the existing `tamper` helper does.
   - Custom transports keep wrapping on top of this.
5. **Diagnostics (see "Related observation" below).** When `fetchVerifiedBundles` or `open` rejects with
   `NO_VERIFIED_BUNDLE` in a test that does not expect it, the failure message includes, for each listed bundle:
   - the `BundleError` code from calling `verifyBundle` directly;
   - the `AttestationError` `check`/`code` from calling `verifyAttestation` directly.
