# D-02 First-bundle NOT_YET_VALID cascade: a fresh token is rejected, and every later open in the run fails

- Severity: **Medium** (triaged by Tech Lead; was High provisional). It breaks the FR-4 vertical slice intermittently and may affect production clients (see Q2).
- Component: under triage. Candidates: `@teecustody/core` bundle and attestation verification (time source or caching); `teecustody-sim` token minting; the T-31 harness.
- Found by: QA (D-01 item 5 diagnostics, branch `inc-2/QA-D-01` at db28d3b), 2026-10-15. Filed by the Orchestrator (D-062 item 2).

## Evidence (QA)
- About 60 runs of `tests/acceptance/FR04.channel-e2e.test.ts` on intermediate D-01 code hit the cascade 5 times. One more came in a full-suite run, where 14 FR-4 tests failed; the rerun was green. The final D-01 code passed 30 runs with no cascade.
- Every capture showed `verifyBundle` → `ATTESTATION_FAILED`, with `verifyAttestation` → check `time`, code `NOT_YET_VALID`.
- With timing fields captured: the token's `nbf` and `iat` were **0.9–1.26 s ahead of the client's `now`**, with `exp` at +3600 s.
- It happens on the first bundle after harness start. Once it occurs, every later open in the run fails.

## Facts established by the Orchestrator
- `packages/teecustody-core/src/attestation/checks/claims.ts:49`: `nbf * 1000 > nowMs` ⇒ `NOT_YET_VALID`, with **zero leeway**. By contrast, `iat` may be up to `token_max_age_s` in the future (line 45).
- The simulator mints with `int(self._clock())` (`simulator.py:306`), so it truncates: `nbf`/`iat` ≤ the issuer's real time. A token ahead of the client's clock on one host therefore means the client compared against a **stale `now`**, read before the token was minted. Alternatively, a test or harness clock is offset.
- The spec (§6, line 365) lists `nbf` as OPTIONAL for the simulator. Neither the spec nor INC-2-API gives a clock-skew leeway for `nbf`.

## Questions
- **Q1 (root cause; Tech Lead):**
  - Where does the stale `now` come from: a cached clock read in ChannelClient, bundle fetch or verification, the test's clock injection, or the harness?
  - Why does the failure cascade to every later open? Is a failed bundle, a negative result or a `now` cached?
  - Which component and task own the fix?
- **Q2 (design; Architect + Security Architect):** real clients' clocks differ from Google's issuer by seconds to minutes. A zero-leeway `nbf` check rejects every fresh token from an issuer whose clock is ahead of the client's, until the client's clock catches up.
  - Should the §6 time checks have a bounded, profile-configured leeway?
  - Any change to §6 semantics or to the trust profile is human-gated.

## Triage (Tech Lead, 2026-10-15)

### (a) Root cause of NOT_YET_VALID: the host wall clock steps backwards (environmental)
- **No stale `now` in the product.** Core reads the clock at every check. `ChannelClient.fetchVerifiedBundles` passes `now: () => clock.now()`, and `verifyAttestation` calls `checkTime(t, profile, deps.now())` at the time step. `verifyBundle` reads `deps.now()` again for pre-key expiry. Router deadlines and `resolveBundle` also read `clock.now()` on each use. `systemClock.now` is `Date.now()`. Nothing caches a time, a bundle, a verification result or an instance. The client cannot read `now` before the first bundle is minted: `startHarness` resolves only on the ready line, and the harness prints that line after the first bundle is listed. QA's diagnostics call `verifyBundle`/`verifyAttestation` again with a fresh `Date.now()` and get the same result, which rules out a cached `now`.
- **The host clock is not monotonic.** On this WSL2 host, `systemd-timesyncd` (poll 32 s, `timedatectl timesync-status` offset −2.18 s) and the Hyper-V host time sync pull `CLOCK_REALTIME` in opposite directions. A 25-minute sampler of `time.time() − time.monotonic()` showed a backward step of **−2.15 to −2.29 s every ~30 s** (17:16:56 … 17:19:57). `dmesg` also shows 49 `systemd-journald: Time jumped backwards` entries in 32 h of uptime. That count is a lower bound, because journald logs a jump only when it writes. Node `Date.now()` and Python `time.time()` agree to within 2 ms between steps.
- **Mechanism.** The workload mints one token at boot (`int(time.time())`) and puts it in every bundle for the run, refreshing it only near expiry. If the clock steps back by S seconds while the token is younger than S, `nbf` leads every client `now` for S minus the token's age. With S ≈ 2.2 s and a step every ~32 s, about 2.2/32 ≈ 7% of runs should be hit. QA saw 5 of 60 (8%), and every measured lead (0.9–1.26 s) is below S.
- **Correlation.** QA's captures have no wall-clock timestamps, so they cannot be lined up with individual steps. The evidence is statistical (rate and amplitude) plus the reproduction below.

### (b) The cascade: time-bounded, no caching
- Each failing open throws `NO_VERIFIED_BUNDLE` in 10–20 ms. The rest of `FR04.channel-e2e.test.ts` therefore runs inside the step window, about 1.5 s, and **every** bundle-dependent test fails. The only tests that pass are the 4 that expect `NO_VERIFIED_BUNDLE` or do not open.
- Reproduction (scratch harness copy; the issuer clock leads by S until the ready line, which is what a client sees after a backward step of S right after the mint):
  - S = 2.5 s and S = 6 s: **14 failed / 4 passed**, file duration 1.9 s. This is the exact count of the full-suite capture.
  - S = 2.5 s, with the ready line held for 3 s: 18/18 green.
  - One `ChannelClient` retrying `open` every 250 ms: `NOT_YET_VALID` with `nbf` lead 1.83 → 1.57 → … → 0.23 s, then **OK at t+2.2 s, with the same client and the same token**. Recovery is immediate, which shows nothing negative is cached.
- **Product question (for Q2).** Nothing in the product is defective. But a freshly booted or refreshed workload is unusable for a client whose clock lags the issuer, from the moment the token is minted until the client's clock passes `nbf`. Core fails at once and does not retry (correct under the INC-2-API contract). With one instance, every open in that window fails. That is exactly the Q2 skew question.
- Minor observation for Q2: `resolveBundle` checks freshness with `now - verifiedAtMs <= bundleMaxAgeMs`. A backward step lengthens a caller-held bundle's freshness by the size of the step. Token `exp` still bounds it. Low.

### Production, independent of Q2
- No stale-`now` path exists, so a long-lived browser client reads `Date.now()` fresh on every open.
- Production is exposed to the same failure class through any wall-clock discontinuity: NTP step corrections, resume from sleep, or a user changing the clock. Each causes the same transient window after a boot or token refresh. The duration is the clock lag minus the token's age, and it fails closed. That is Q2's exposure, not a separate defect.
- CI runners on Linux slew rather than step for small offsets, so the flake is unlikely in CI.

### Owner and fix route
- **No Core (T-26/T-12), simulator or T-31 code defect.** Nothing in the product needs a fix.
- (a) is the dev host's configuration. The human could run a single time source on the WSL2 host, for example by disabling `systemd-timesyncd` and keeping the Hyper-V sync. That is the human's call; the team does not change machine config.
- (b)/Q2 belongs to the **Architect and Security Architect**: a bounded, profile-configured `nbf`/`iat` leeway under spec §6.4. This is PROCESS §6 row 5 and is human-gated.
- Optional interim fix, local to T-31 (§6 row 1, test-only): the harness holds the ready line until the boot token is at least 3 s old. A backward step can then only break a run if it exceeds 3 s. The control run above shows this works. Recommended until Q2 is decided.

### Severity: **Medium** (down from High provisional)
- No security impact: it fails closed and nothing is accepted that should not be.
- Availability only, and transient: it self-heals once the clock passes `nbf`.
- The root cause in this repo is environmental, and no product code is defective.
- The production exposure is real and is tracked as Q2, which decides whether it is fixed now or deferred with the human's sign-off at G6.
