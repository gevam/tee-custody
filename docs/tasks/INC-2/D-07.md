# D-07: a full gateway page at default limits exceeds the documented 1 MiB `FetchTransport` response limit (a busy client's poll fails permanently)

Increment: INC-2   Severity: Medium   Found by: Architect (flagged during T-40 A4); triaged by the Tech Lead
Violates: FR-5 (the gateway and `FetchTransport` contracts must interoperate at their documented values), SR-4
(availability for in-budget callers). INC-2-API §6 `max_page`/`max_bundles` versus §8.3 `maxResponseBytes`
("default 1048576").   Affects task(s): T-14 (gateway contract), T-19 (FetchTransport documentation)
Status: open

## Reproduction
Run against main using a scratch script; no repository file changes.
1. `q = InMemoryQueue()`. Publish 32 responses for one client. Each body is the CDDL-maximal frame-result envelope:
   `encode_response_envelope("frame_result", encode_frame_aad(FrameAad(b"\x11"*16, 2**53-1, "a"*64)), b"\0"*32784)`,
   which is 32,926 bytes.
2. `TestClient(create_app(q)).get("/responses/<client>")` → `200`, 32 items, **1,406,811 bytes**.
3. With 16 bundles of 65,536 bytes (the bundle decode limit), `GET /bundles` gives **1,399,133 bytes**.
4. `FetchTransport` refuses any body over `maxResponseBytes` with `INVALID_RESPONSE` (§8.3). The documented value,
   and the one the repository's harnesses use, is 1,048,576. That fits at most 23 maximal frames.

Expected: at the gateway's default limits, a protocol-valid page always fits the client's documented limit.
Actual: a client with 24 or more maximal pending responses gets `INVALID_RESPONSE` on every poll. The cursor
cannot advance, so the client can never collect its responses. Availability only: nothing leaks, and an attacker
cannot fill a victim's route with large responses, because only the victim's own session produces them.

## Environment
Branch/commit: main 2684805   Data/fixture: `InMemoryQueue`, default `GatewayLimits`   Notes: sizes are exact
because the JSON is deterministic.

## Suspected area
The contract numbers, not code. `maxResponseBytes` is a required option: `fetch-transport.ts` has no default, only
the comment "default 1048576". The gateway cannot trim a page by bytes without a cursor per item, which the
`RelayQueue` port does not have.

## Fix contract
Route (b): derive the client's documented limit from the gateway contract.
- The Architect adds to §6 the maximal page sizes at the default limits.
- §8.3 then says "recommended 2097152", which must be at least the §6 maximal page.
- The Architect re-checks the §6 write-deadline sizing for 2 MiB: about 70 KB/s at 30 s.
- Implementation: T-40 A5 (gateway README, guard test, and the one comment line in `fetch-transport.ts`).
- Lowering the gateway's `max_page` to 16 instead was rejected: it changes a §6 default, and QA rows assert 32.
