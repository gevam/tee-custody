## Interface contract
INC-2-API §4.6 verbatim:
```python
KEM_ID: Final = 0x0020; KDF_ID: Final = 0x0001; AEAD_ID: Final = 0x0002   # Base mode only
EXPORT_C2T: Final = b"c2t"; EXPORT_T2C: Final = b"t2c"; EXPORT_LENGTH: Final = 32
class HpkeErrorCode(StrEnum): OPEN_FAILED = "OPEN_FAILED"; INVALID_KEY = "INVALID_KEY"
def generate_keypair() -> tuple[Secret, bytes]: ...        # X25519 via `cryptography`; (raw private, raw public)
@dataclass(frozen=True, slots=True, eq=False)
class OpenedHpke: plaintext: Secret; sk_c2t: Secret; sk_t2c: Secret
def open_base(private_key: Secret, enc: bytes, info: bytes, aad: bytes, ct: bytes) -> OpenedHpke: ...
    # Setup Base receiver, Open once, then Export("c2t",32) and Export("t2c",32) from the same context.
    # Any library failure (bad enc, all-zero DH, tag mismatch) → HpkeError(OPEN_FAILED); cause discarded.
    # The caller wipes private_key in `finally` whether or not this raises (spec §5.4 step 14).
```
ADR 0011 C1 (`pyhpke` over `cryptography`), C2 (no HPKE/HKDF composition here), C5 (no `eks`, PSK, PSK id or
sender-key parameter exists or is passed). `INVALID_KEY`: `private_key` not 32 bytes or wiped. Exceptions are
raised `from None`. The suite object is built once at import:
`CipherSuite.new(KEMId.DHKEM_X25519_HKDF_SHA256, KDFId.HKDF_SHA256, AEADId.AES256_GCM)`.

## Acceptance criteria (each becomes a test, in this order)
1. Given `generate_keypair()`, then the public key is 32 bytes and equals the X25519 public key of the revealed
   private key (`cryptography`); two calls differ.
2. Given a sender context built in the test with `pyhpke` (tests may import it) to the public key, when
   `open_base` runs with the same `info`/`aad`, then `plaintext` matches and `sk_c2t`/`sk_t2c` equal the sender's
   `export(b"c2t", 32)`/`export(b"t2c", 32)`.
3. Given a wrong `info`, a modified `aad`, a one-bit `ct` flip, a 31-byte `enc`, an all-zero `enc` and a
   low-order `enc` (RFC 7748 §6.1 point list), then `HpkeError(OPEN_FAILED)` with `__cause__` and
   `__context__` both `None` and `str(err) == "OPEN_FAILED"`.
4. Given a wiped or 31-byte private key, then `HpkeError(INVALID_KEY)`.
5. KAT (`tests/fixtures/rfc9180/test-vectors.json`, SHA-256 asserted against its README): filter to (mode 0,
   0x0020, 0x0001, 0x0002) and to A.1 (mode 0, 0x0020, 0x0001, 0x0001); assert each set is non-empty; for each
   case: `pyhpke` DeriveKeyPair(ikmE/ikmR) → pkEm/pkRm; a `pyhpke` recipient context opens every listed
   encryption in order and matches every listed export; for the first encryption of each 0x0002 case,
   `open_base(Secret(skRm), enc, info, aad, ct)` returns `pt`.
6. Given `inspect.signature` of `open_base` and `generate_keypair`, then no parameter is named `eks`, `psk`,
   `psk_id`, `sks` or `pks`.
7. Given the modified requirement tests, then `teecustody` and `teecustody-sim` each require exactly the old
   pins plus `pyhpke==<version>`.
