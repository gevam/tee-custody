# T-09: Validate `ChannelParams` and `BoundaryLimits` (`config.py`)

Increment: INC-2   Wave: 1   Tier: STRONG (security.paths: `teecustody/config.py`)   Depends on: T-04

## Goal
Every channel parameter and boundary limit is rejected at construction when out of range, so no workload
can start with an unbounded queue pull, replay cache, session table or decode limit.

- `packages/teecustody-py/src/teecustody/config.py` (stub from T-04: add `__post_init__` to both dataclasses
  and private helpers; fields, defaults, `ConfigError`, `ConfigErrorCode` are frozen)
- `packages/teecustody-py/tests/test_config.py` (create)

Touching any other file is out of scope — return CONTRACT_ISSUE instead.

## Interface contract
INC-2-API §4.4 verbatim (fields, defaults and range comments are normative). Key text:
> `__post_init__` rejects any value that is not a finite positive number of the declared type (bool is not an
> int), any `DecodeLimits` field < 1 or `max_depth` > 16, and the cross-field rules above. `RunLoop.__init__`
> checks the one rule that spans both objects (`session_evict_min_idle_s <= idle_timeout_s`).

Ranges (from the §4.4 comments): `prekey_ttl_s` 60..3600; `prekey_batch` 1..256; `prekey_low_water`
0 ≤ x < `prekey_batch` (the only field where 0 is allowed); `request_skew_s` 1..3600; `idle_timeout_s`
1..86400; `refresh_margin_s` 1..3599; `pull_wait_s` 0 < x ≤ 30 and finite; `attestation_retry_max_s` ≥
`attestation_retry_min_s`. Every other int field ≥ 1. `pull_wait_s` accepts `int` or `float` (not `bool`).
`DecodeLimits` fields must be exact `int` (not `bool`). Errors: `ConfigError(INVALID_PARAMS, field)` from
`ChannelParams`, `ConfigError(INVALID_LIMITS, field)` from `BoundaryLimits`; the field is the first failing
field in declaration order (cross-field rules are checked after all single-field rules; the reported field is
the second field of the rule, e.g. `prekey_low_water`, `attestation_retry_max_s`).

## Acceptance criteria (each becomes a test, in this order)
1. Given defaults, then `ChannelParams()` and `BoundaryLimits()` construct.
2. Given each field set to its lowest and highest valid value, then construction succeeds (parametrized).
3. Given each field set to one below/above its range, `0`, a negative, `True`, a `str`, and (for floats) `nan`
   and `inf`, then `ConfigError` with the right code and `str(err) == f"{code}:{field}"` (parametrized).
4. Given `prekey_low_water == prekey_batch`, then `INVALID_PARAMS:prekey_low_water`.
5. Given `attestation_retry_max_s < attestation_retry_min_s`, then `INVALID_LIMITS:attestation_retry_max_s`.
6. Given a `DecodeLimits` field with `max_bytes=0`, `max_depth=17`, or `max_items=True` in any of the four
   decode-limit fields, then `INVALID_LIMITS:<that field name>` (e.g. `aad_decode`).
7. Given `BoundaryLimits(max_sessions=64)` (the §4.4 example), then success; `BoundaryLimits(pull_wait_s=0)`
   → `ConfigError("INVALID_LIMITS:pull_wait_s")`.
