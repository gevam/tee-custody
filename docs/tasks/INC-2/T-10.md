## Goal
An open message is accepted at most once for exactly as long as its timestamp could still pass the skew
check, with a hard memory bound that never evicts a live entry.

## Interface contract
INC-2-API §4.9 (ReplayCache part) verbatim, with the R-6 clerical fix (D-041):
```python
class ReplayCache:
    def __init__(self, *, skew_s: int, max_entries: int, clock: Callable[[], float]) -> None: ...
    def seen(self, aad_client_id: str, request_id: bytes) -> bool: ...
        # first purges every entry whose expires_at < now (strict: at now == timestamp + skew the entry is still present)
    def record(self, aad_client_id: str, request_id: bytes, timestamp: int) -> None: ...
        # after a successful Open only; expires_at = timestamp + skew_s (R-6; D2-18), so the entry lives exactly
        # as long as the message could still pass the |now - timestamp| <= skew check.
        # full → OverflowError("REPLAY_CACHE_FULL"); never evicts an unexpired entry.
        # The key is the AAD value as received (a replay key, never an identity; for enroll it is the reply route).
```
Decisions: the key is the tuple `(aad_client_id, request_id)`; `record` also purges expired entries before
the capacity check; recording a key already present keeps the larger `expires_at`. Purge cost is amortised
O(1) per call (a min-heap or insertion-ordered structure keyed by `expires_at`). `__init__` raises
`ValueError("SKEW_RANGE")` / `ValueError("MAX_ENTRIES_RANGE")` for values < 1.

## Acceptance criteria (each becomes a test, in this order)
1. Given an empty cache, then `seen` is false; after `record(c, r, now)`, `seen(c, r)` is true and
   `seen(c, other)` / `seen(other, r)` are false.
2. (R-6, SR-14) Given `timestamp = now + skew − 1` recorded at `now`, when the clock reaches
   `now + 2·skew − 2`, then `seen` is true; at exactly `timestamp + skew`, `seen` is true; at
   `timestamp + skew + 1`, `seen` is false and the entry is gone (`len` via a private size helper).
3. Given `max_entries = 3` filled with live entries, when a 4th `record` runs, then
   `OverflowError("REPLAY_CACHE_FULL")` and all 3 entries are still `seen`.
4. Given the same full cache after the clock passes every entry's `expires_at`, then a new `record` succeeds.
5. Given 100 000 records with increasing timestamps and a moving clock, then the run completes within 2 s
   (amortised purge) and memory stays bounded by `max_entries`.
6. Given invalid constructor values, then the specified `ValueError`s.

## Security requirements
