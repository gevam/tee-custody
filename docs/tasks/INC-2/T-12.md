# T-12: Implement the audit emitter: aggregates, capped pre-principal alerts, retries (`audit/emitter.py`)

> **Amendment A1 (2026-10-15, Tech Lead; T-12 Security Review Medium + Lows; PROCESS §6, local to this module).**
> - The single pending queue (24 records, oldest of any class evicted) lets 101 spoofed pre-principal ALERTs push
>   out an uncapped `alert()` such as `PREKEY_BURN_HIGH` during an outage. That breaks SR-12: the cap never
>   applies to authenticated or non-anonymous alerts.
> - The pending store is therefore split into two bounded classes (Decisions A1).
> - The drop log names the dropped outcome.
> - A backward clock jump and invalid constructor arguments are handled.
> - The Architect aligns the INC-2-API §4.12 "pending" sentence to this text. That is text alignment only; no
>   ruling is needed, because the change restores SR-12 inside one module.

## Goal
Anonymous (pre-principal) channel failures become bounded per-interval `AGGREGATE` records with exact
counts, alerts are written individually and never suppressed, and an audit backend outage never breaks the
channel or grows memory without bound.

## Interface contract
INC-2-API §4.12 (emitter part) and §10 verbatim:
```python
class AuditEmitter:
    def __init__(self, sink: AuditSink, *, interval_s: int, alert_cap: int, clock: Callable[[], float],
                 rng: Callable[[int], bytes], logger: AllowListedLogger) -> None: ...
    def count(self, outcome: AggregateOutcome) -> None: ...              # O(1), in memory; saturates at MAX_COUNT
    def pre_principal_alert(self, outcome: str, *, subject_client_id: str, request_id: str | None = None,
                            epoch: int | None = None, recovery_id: str | None = None) -> None: ...
        # first per (outcome, subject_client_id) per interval → ALERT; repeats fold into AGGREGATE `outcome`;
        # beyond alert_cap ALERT objects this interval → one ALERT_CAP_REACHED (exempt from the cap), then fold.
    def alert(self, outcome: str, *, request_id: str | None = None,
              interval: tuple[int, int] | None = None) -> None: ...      # never capped or deduplicated
    def tick(self) -> None: ...       # when the interval has ended: write one AGGREGATE per outcome with count >= 1; retry pending
    def close(self) -> None: ...      # at shutdown: flush the partial interval (interval_end = now)
```
> Object ids: `AGGREGATE` `<interval_start_ms>/<outcome>/<hex(rng(8))>`; `ALERT` `<hex(rng(16))>/<outcome>`.
> `ALREADY_EXISTS` on any write → `alert("AUDIT_WRITE_CONFLICT", request_id=…)` with a fresh id. `UNAVAILABLE` →
> the record stays pending and is retried on each `tick`, at most `2 × len(AggregateOutcome)` pending records;
> beyond that the oldest is dropped and `AUDIT_PENDING_DROPPED` is logged. The emitter never raises into the channel.

Decisions (TL): interval clock in Unix ms = `int(clock() * 1000)`; the first interval starts at construction;
intervals are contiguous (`start_{k+1} = start_k + interval_s·1000`); an ended interval's AGGREGATEs carry that
interval's `interval_start`/`interval_end`; `ts` = write time in ms. Only `pre_principal_alert` ALERTs count
toward `alert_cap`; dedup set and cap counter reset per interval. `AUDIT_WRITE_CONFLICT` carries the
conflicting record's `request_id` (or none) and is not retried on conflict again. Any exception from the
sink other than `AuditError(UNAVAILABLE)` (including `INVALID_ARGUMENT`) is logged as `AUDIT_WRITE_FAILED`
and the record dropped. Validation of identifiers is the sink's job (T-11 via adapters).

Decisions A1 (supersede the single-queue sentence above):
- **Two pending classes.**
  - *Protected*: every record from `alert()` (including `AUDIT_WRITE_CONFLICT` and `PREKEY_BURN_HIGH`) and
    every `ALERT_CAP_REACHED`.
  - *Sheddable*: pre-principal ALERTs from `pre_principal_alert` and AGGREGATEs.
- **Bounds.** Sheddable is at most `2 × len(AggregateOutcome)` (24), and its overflow drops the oldest
  *sheddable* record. Protected is at most `PROTECTED_PENDING_MAX: Final = 256` (module constant), and its
  overflow drops the oldest *protected* record.
- **Isolation.** Sheddable pressure never evicts a protected record.
- **Retry order** on `tick` and `close`: protected first, oldest first, then sheddable.
- **Drop log.** It is the outcome string `AUDIT_PENDING_DROPPED_<dropped record's outcome>` (no fields). If that
  string exceeds 64 characters or fails `OUTCOME_PATTERN`, the log is plain `AUDIT_PENDING_DROPPED`.
- **Backward clock.** If `tick` sees `now_ms < interval_start`, the current interval ends at its nominal end
  (`interval_start + interval_s·1000`, so the record fields stay valid). The next interval starts at `now_ms`.
  The log `AUDIT_CLOCK_BACKWARD` (no fields) is written once per occurrence.
- **`close()` at the interval start** (A2, accepted by the Code Reviewer). If `now_ms == interval_start`, the
  partial interval is written with `interval_end = interval_start + 1`, because `validate_audit` rejects
  `start >= end`. In every other case `interval_end = now`.
- **ALERT_CAP_REACHED** (A2, corrected; SR Low). At most **one** pending `ALERT_CAP_REACHED` in total, across
  all intervals.
  - The earliest is kept. Any later one, raised while one is still pending, is dropped and logged as
    `AUDIT_PENDING_DROPPED_ALERT_CAP_REACHED`.
  - So under any outage length, the protected class holds at most 255 `alert()` records plus one cap event.
  - The per-interval AGGREGATE counts still record every folded alert.
- **Constructor.** `interval_s` must be an `int` (not `bool`) in 10..900, and `alert_cap` an `int` (not `bool`)
  in 1..10 000 (the INC-2-API §4.4 ranges). Anything else raises `ValueError("INVALID_EMITTER_CONFIG")`.
  `AuditEmitter` is public, so it does not rely on T-09's validation having run.

## Acceptance criteria (each becomes a test, in this order; fake sink + fake clock + fixed rng)
1. Given N calls of `count(X)` for each `AggregateOutcome` within one interval, when `tick` runs after it ends,
   then exactly one AGGREGATE per outcome with `count == N`, correct interval fields and id format;
   outcomes with zero calls write nothing.
2. Given `count` called `MAX_COUNT + 5` times (simulate via a private counter seed), then `count == MAX_COUNT`.
3. Given `pre_principal_alert("KCV_MISMATCH", subject=a)` twice and for subject b once, then two ALERTs (a, b)
   and the repeat folds into AGGREGATE `KCV_MISMATCH` count 1 at interval end.
4. Given `alert_cap = 2` and 5 distinct subjects, then 2 ALERTs, one `ALERT_CAP_REACHED`, and 3 folded counts;
   the next interval starts a fresh cap.
5. Given 200 `alert("PREKEY_BURN_HIGH", interval=(s, e))` calls, then 200 ALERT records with the interval and
   no `count` (never capped or deduplicated).
6. Given the sink returns `ALREADY_EXISTS`, then an `AUDIT_WRITE_CONFLICT` ALERT is written with a new id.
7. Given the sink raises `UNAVAILABLE` for 30 sheddable writes, then at most `2 × 12` sheddable records stay
   pending, and the oldest are dropped with their outcome-named drop log (A1), and pending records are written on the next successful `tick`.
8. Given `close()` mid-interval, then the partial interval is flushed with `interval_end` = now. Given `close()`
   exactly at the interval start, then `interval_end = interval_start + 1` (A2).
9. Given a sink raising any exception, then no emitter method raises; logs contain only allow-listed fields.
10. (A1, the reviewer's PoC) Given the sink `UNAVAILABLE`, when `alert("PREKEY_BURN_HIGH")` is raised and then 101
    distinct-subject `pre_principal_alert("KCV_MISMATCH", …)` follow, and the sink then recovers and `tick`
    runs, then `PREKEY_BURN_HIGH` is written. The logs name every dropped record by its
    `AUDIT_PENDING_DROPPED_<OUTCOME>` string. No `alert()` record is dropped.
11. (A1) Given 257 `alert()` calls while the sink is unavailable, then the oldest one is dropped with its
    outcome-named log. 256 are written after recovery, in order.
12. (A1) Given the fake clock moved backwards mid-interval, then the next `tick` writes the AGGREGATEs with
    `interval_end = interval_start + interval_s·1000`, logs `AUDIT_CLOCK_BACKWARD` once, and starts the next
    interval at the new `now`.
13. (A1) Given `interval_s` of 0, 9, 901 or `True`, or `alert_cap` of 0, -1, 10 001 or `True`, then the
    constructor raises `ValueError("INVALID_EMITTER_CONFIG")`.
14. (A2) Given the sink `UNAVAILABLE` across 300 intervals, each hitting the cap, and one `alert("PREKEY_BURN_HIGH")`
    in the first interval, then one `ALERT_CAP_REACHED` (the earliest) and `PREKEY_BURN_HIGH` are written after
    recovery. Every later cap event logged `AUDIT_PENDING_DROPPED_ALERT_CAP_REACHED`, and no `alert()` record was
    dropped.

## Security requirements
- SR-6 / SR-12 (INC-2-API §14): criteria 1, 4, 5, 6 — aggregates with exact counts; `PREKEY_BURN_HIGH` and
  `AUDIT_WRITE_CONFLICT` never capped; flood produces `ALERT_CAP_REACHED`.
- SR-11: criterion 9 (no record content or exception text in logs).

## Constraints
- No new dependencies. Logging only `AUDIT_PENDING_DROPPED` / `AUDIT_PENDING_DROPPED_<OUTCOME>`,
  `AUDIT_WRITE_FAILED` and `AUDIT_CLOCK_BACKWARD` (A1), all with no fields.
