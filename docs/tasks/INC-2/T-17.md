# T-17: Adopt `@hpke/core` and implement the WebCrypto `Crypto` adapter (`crypto/webcrypto.ts`)

Increment: INC-2   Wave: 1   Tier: STRONG (security.paths: Web `src/crypto/**`; crypto dependency)   Depends on: T-02, V-01 (C6 amendment signed off), V-02 (V-2.6 facts)
Requirements covered: FR-4, NFR-4, NFR-5, SR-1 (B-06 modulus), SR-9 (C3, C6), SR-14 (C3–C5)

## Goal
Browsers and Node ≥ 22 get one `Crypto` capability whose every primitive is native WebCrypto, whose HPKE is
`@hpke/core` Base mode on native X25519 with no seams and no JS-curve fallback, proven by the CFRG vectors.
This task is the JS lock-file adoption of ADR 0011; it merges only after V-01's C6 amendment is signed off.

## Interface contract
INC-2-API §8.1 verbatim:
```ts
export interface WebCryptoOptions {
    readonly subtle?: SubtleCrypto;                                   // default globalThis.crypto.subtle
    readonly getRandomValues?: (a: Uint8Array) => Uint8Array;         // default globalThis.crypto.getRandomValues
}
export function createWebCrypto(options?: WebCryptoOptions): Crypto;   // works in browsers and Node >= 22
```
> `randomBytes(n)`: 1 ≤ n ≤ 65536 else `INVALID_ARGUMENT`. `verifyEd25519(pk, data, sig)`: pk 32 / sig 64 else
> `INVALID_ARGUMENT`; WebCrypto `Ed25519` missing → `UNSUPPORTED`; import failure → `INVALID_ARGUMENT`;
> mismatch → `false`. `verifySignature`: INC-1 contract unchanged; modulus < 2048 → `INVALID_ARGUMENT` (read
> from the imported key). `setupHpkeSender(pkR, info)` / `setupHpkeReceiver(skR, enc, info)`: `@hpke/core`
> `CipherSuite` with `DhkemX25519HkdfSha256`, `HkdfSha256`, `Aes256Gcm`, Base mode (no PSK, no sender key).
> Native WebCrypto X25519 missing → `UNSUPPORTED`; never a JS curve fallback (ADR 0011 C3, T-28). Neither
> function takes, nor passes to `@hpke/core`, an `ekm`, PSK, PSK id or sender key (C5; ESLint rule). This file
> is the only `@hpke/*` import site in the packages. Key length ≠ 32 → `INVALID_ARGUMENT`; open failure →
> `AUTHENTICATION_FAILED`; `export` label ≤ 64 bytes, length 1..64. `destroy()` drops the context; a later
> call → `INVALID_ARGUMENT`. `aes256GcmEncrypt/Decrypt`: key 32, nonce 12 else `INVALID_ARGUMENT`; output
> `ct ‖ tag`; tag failure → `AUTHENTICATION_FAILED`.

Decisions: `sha256` via `subtle.digest`; every `CapabilityError` is thrown with no cause; X25519 support is
probed once per adapter (`subtle.generateKey({name: "X25519"}, …)`; failure → every HPKE call rejects
`UNSUPPORTED`); Ed25519 likewise. Inputs are copied (`slice()`) before passing to WebCrypto. `verifySignature`
with an algorithm other than `RSASSA_PKCS1V15_SHA256` → `UNSUPPORTED_ALGORITHM`.

## Acceptance criteria (each becomes a test, in this order; Node 22 vitest)
1. Given `randomBytes(0)`, `(65537)`, then `INVALID_ARGUMENT`; `randomBytes(32)` twice differ.
2. Given a WebCrypto Ed25519 keypair, then valid → `true`, bit-flipped → `false`, 31-byte key / 63-byte sig →
   `INVALID_ARGUMENT`; with `subtle` whose Ed25519 import throws `NotSupportedError` → `UNSUPPORTED`.
3. (B-06) Given a 1024-bit RS256 JWK, then `verifySignature` → `INVALID_ARGUMENT`; 2048-bit valid → `true`.
4. Given sender → receiver round trip, then plaintext and both exports (`c2t`, `t2c`, 32 bytes) agree; wrong
   `info`, modified aad, flipped ct → `AUTHENTICATION_FAILED`; 31-byte `pkR`/`skR`/`enc` → `INVALID_ARGUMENT`;
   all-zero and low-order `enc` → `AUTHENTICATION_FAILED`; any call after `destroy()` → `INVALID_ARGUMENT`;
   export length 0 or 65, or label of 65 bytes → `INVALID_ARGUMENT`.
5. Given a `subtle` without X25519 (generateKey rejects), then `setupHpkeSender`/`Receiver` → `UNSUPPORTED`
   and no `@hpke` code path imports a JS curve (assert the module graph has no `@hpke/dhkem-x25519`).
6. Given AES-GCM with a 31-byte key or 11-byte nonce → `INVALID_ARGUMENT`; tag flip → `AUTHENTICATION_FAILED`;
   output length = plaintext + 16.
7. KAT (`tests/fixtures/rfc9180/test-vectors.json`, SHA-256 asserted): filter (mode 0, 0x0020, 0x0001, 0x0002)
   and A.1; assert each non-empty; per case: DeriveKeyPair(ikmE/ikmR) → pkEm/pkRm via `@hpke/core` in the test;
   sender side via `@hpke/core` with `ekm` injection **in the test file only**; receiver side via the adapter's
   `setupHpkeReceiver(skRm, enc, info)` opening every encryption in order and matching every export.
8. Given `Function.prototype.toString` of `setupHpkeSender`/`setupHpkeReceiver`, then their parameter lists are
   exactly `(recipientPublicKey, info)` / `(recipientPrivateKey, encapsulatedKey, info)` (C5).
