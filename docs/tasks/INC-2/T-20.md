## Goal
The client share is persisted only as AES-GCM ciphertext under a non-extractable key derived from WebAuthn
PRF output, and every capability gap fails closed with nothing written.

## Interface contract
INC-2-API §8.4 verbatim (options, class, stored record, key derivation, ceremonies, errors):
```ts
export class PrfShareVault implements ShareVault {
    constructor(options: PrfShareVaultOptions);
    get(client: ClientId): Promise<ClientShare | undefined>;
    set(client: ClientId, share: ClientShare): Promise<void>;
    clear(client: ClientId): Promise<void>;
}
```
> **Stored record** (IndexedDB `dbName`, version 1, object store `shares`, keyPath `client_id`). Only these
> fields, no plaintext: `{ v: 1, client_id, credential_id: Uint8Array, prf_salt: Uint8Array(32), nonce:
> Uint8Array(12), ct: Uint8Array(48) }`. **Key derivation.** PRF eval input `first = prf_salt`. Wrapping key =
> WebCrypto HKDF-SHA256(ikm = PRF output `first` (32 B), salt = `prf_salt`, info = `ascii("teecustody/vault/v1")
> ‖ 0x00 ‖ ascii(client_id)`) → AES-GCM-256, **non-extractable**, usages encrypt/decrypt. Encryption: AES-256-GCM,
> random 12-byte nonce, aad = `encodeCanonical(Map{"v":1,"client_id":…,"credential_id":…})`.

Ceremonies and errors exactly as §8.4 ("`userVerification: "required"` … No path falls back to weaker
storage"). TL decisions: TL-6 (WebAuthn absent iff the resolved credentials container is `undefined`;
`indexedDB` absent → `UNAVAILABLE`); `create` uses `rp`, `user.id` = 16 fresh random bytes,
`user.name`/`displayName` from `options.user(client)`, `pubKeyCredParams` `[{type:"public-key",alg:-8},
{type:"public-key",alg:-7}]`, `authenticatorSelection {residentKey:"required", userVerification:"required"}`,
`challenge` 32 random bytes; `get` uses `allowCredentials: [{type:"public-key", id: credential_id}]`,
`challenge` 32 random bytes. The constructor validates `rp.id`/`rp.name` non-empty strings, `timeoutMs`
positive safe integer, `dbName` non-empty (else `TypeError("INVALID_CONFIG")`). PRF output must be exactly 32
bytes, else `UNSUPPORTED`. The returned `rawId` of `get` must equal the stored `credential_id`, else
`AUTHENTICATION_FAILED`. Temporary buffers holding the share or PRF output are zeroed with `fill(0)` after use.

## Acceptance criteria (each becomes a test, in this order; `fake-indexeddb` + `fake-authenticator.ts`, whose PRF
is HMAC-SHA-256(secret, salt) via WebCrypto and which records every ceremony argument)
1. Given PRF available, when `set` then `get`, then the same 32 bytes are returned as a fresh buffer; mutating the
   caller's input after `set` does not change the stored value.
2. Given the store after `set`, then the record has exactly the six fields with the stated lengths, and the share
   bytes, their hex and base64 forms appear nowhere in IndexedDB, `localStorage` (a polyfill in the test) or
   `document.cookie` (stub) (INC-2-API §14 FR-6 scan).
3. Given `create`, then `user.id` is 16 bytes, differs between two vaults, and never equals `client_id` bytes;
   `extensions.prf` was requested and `userVerification` is `"required"` in both ceremonies.
4. Given PRF results returned only by `get` (V-2.5 Chromium shape) and only by `create`, then both paths work.
5. Given no credentials container, `prf.enabled !== true`, PRF results missing, a 31-byte PRF output, or a
   WebAuthn `SecurityError`/`NotSupportedError`, then `UNSUPPORTED` and the `shares` store is empty.
6. Given `NotAllowedError` or `AbortError`, then `USER_PRESENCE_REQUIRED`; nothing written.
7. Given a stored record with a flipped `ct` byte, a flipped `nonce` byte, a changed `credential_id`, a
   mismatching returned `rawId`, or an extra field, then `get` → `AUTHENTICATION_FAILED`.
8. Given `indexedDB` absent or a failing transaction, then `UNAVAILABLE`.
9. Given `client` not 32 lowercase hex or a share ≠ 32 bytes, then `INVALID_ARGUMENT` before any ceremony.
10. Given no record, then `get` → `undefined` with zero ceremonies; `clear` twice succeeds.
11. Given a second `set` for the same client, then the credential is reused (no `create`) with a fresh
    `prf_salt` and `nonce`.
12. Given the derived `CryptoKey`, then `extractable === false` and usages are exactly encrypt/decrypt.
13. (§8.4 a) Given a credentials double whose `getClientCapabilities` returns `{"extension:prf": true}` and whose
    `create` returns `prf.enabled: false`, then `set` → `UNSUPPORTED` and the `shares` store is empty.
14. (§8.4 b) Given the same double with `prf.enabled: true` but no `results` from `create` or `get`, then
    `UNSUPPORTED` and the store is empty.
15. (§8.4 c) Given `results.first` of length 31 and of length 33, then `UNSUPPORTED` and the store is empty.
16. (§8.4 d) Given the text of every file under `src/vault/`, then it contains neither `getClientCapabilities` nor
    `isUserVerifyingPlatformAuthenticatorAvailable`. Read the files with `node:fs` in the test.
