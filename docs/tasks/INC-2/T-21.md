## Goal
The simulator behaves like Google on CORS. It emits only v2 profiles with an exact loopback `jwks_uri`. It
serves a same-origin attacker JWKS, and it mints the two T-29 vector rows, so every client can prove that only
the pinned URI decides.

## Interface contract
INC-2-API §16.3 verbatim: `ATTACKER_JWKS_PATH`; `IssuerServer(..., attacker_jwks=None)`; the routes table and
the "never sent" list; `SimKeys.attacker_issuer_kid`, `attacker_jwks()` and `sign_jws_attacker`; rows 38
(`jwks_other_path`) and 39 (`jwks_other_path_same_kid`); the `token.py` rule; `Simulator.jwks_uri` and
`attacker_jwks_uri`; `sim-state.json` v2; and `build_trust_profile(*, jwks_uri, ...)` with
`INVALID_JWKS_URI`. Plus §16.4 for `vectors.py`: v2 `profile_json`, v2 `production_profile_json`, and an
`http` map of exactly three entries with no discovery URL.

Security Architect condition **L-1** (D-047), which is binding:
- The attacker key is generated fresh per state directory (`keys/attacker-issuer.pem`, PKCS#8, mode 0600),
  like the issuer key. It is never committed, served, printed or logged, and never written to vectors.
- `sign_jws_attacker` is called only from the `jwks_other_path*` branch of `mint` (CLI `token --case
  jwks_other_path*`, vectors, and test minters). The launcher socket path never calls it.
- `vectors.py` generates its own fresh keys as today and never reads the state directory.

Decisions:
- `Access-Control-Allow-Origin` is `*` (pending CI-2-4).
- The 404/405/431/503 paths stay unchanged.
- The preflight is answered only for `/jwks`, and for `/attacker/jwks` when it is set.

## Acceptance criteria (each becomes a test, in this order; INC-2-API §16.9 S1–S6)
1. (S1) Given `GET /jwks` and `GET /attacker/jwks` with `Origin: http://127.0.0.1:5555`, then 200 with
   `Access-Control-Allow-Origin: *`. Given `OPTIONS` with `Access-Control-Request-Method: GET`, then 204 with
   exactly the two headers and no `Content-Type`. Given a discovery `GET`, then 200 with no
   `Access-Control-*` header. Given a 404, 405, 431 or 503, then no `Access-Control-*` header.
   `Access-Control-Allow-Credentials`, `-Allow-Headers`, `-Max-Age`, `-Expose-Headers` and `Vary` never appear.
2. (S2) Given `teecustody-sim profile --out P`, then `profile_version` is 2, `jwks_uri ==
   simulator.jwks_uri`, and neither `discovery_url` nor `jwks_origin` is present. The Node half of S2 is
   covered by T-36's acceptance test and T-33's contract test.
3. (S3) Given the row 38 and row 39 tokens, then each verifies with `cryptography` RS256 under the
   attacker-JWKS entry named by its header `kid`, and fails under the `/jwks` key set.
4. (S4) Given `build_trust_profile` with port 80, a leading-zero port, a path other than `/jwks`, a
   non-loopback host, `https:` or a trailing slash, then `ValueError("INVALID_JWKS_URI")`, raised before any
   other validation.
5. (S5) Given a v1 `sim-state.json`, then `teecustody-sim profile` exits with `STATE_NOT_INITIALISED`.
6. (S6, L-1) Given a running simulator, then the `/jwks` body never contains the attacker modulus. Given a
   launcher-socket token, then it never verifies under `/attacker/jwks`. Given two state directories, then
   their attacker keys differ. Given `repr(SimKeys)` and the CLI output of every command, then neither
   contains attacker PEM or modulus text.
7. Given `NEGATIVE_CASES`, then there are 38 rows in the INC-2-API order (rows 2..39), and
   `teecustody-sim token --case jwks_other_path` and `--case jwks_other_path_same_kid` work.
8. Given `generate_suite`, then the `http` keys are exactly the three §16.4 URLs, and none ends in
   `/.well-known/openid-configuration`.
9. Given the two contract files, then they assert S1, S2 and the v2 state keys, and no assertion names
   `jwks_origin`.
