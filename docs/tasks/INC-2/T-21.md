## Goal
A browser page on another loopback origin can fetch the simulator's OIDC discovery document and JWKS exactly
as it can fetch Google's, so the browser harness (T-32) exercises the real verification path.

## Owned files
- `packages/teecustody-sim/src/teecustody_sim/issuer.py` (modify: response headers on the two GET routes only)
- `packages/teecustody-sim/tests/test_issuer_cors.py` (create)

Touching any other file is out of scope — return CONTRACT_ISSUE instead.

## Interface contract
For `GET <discovery path>` and `GET <jwks path>` answered with 200, add exactly the CORS response headers
V-02 recorded for production (expected: `Access-Control-Allow-Origin: *`; copy any `Vary` header value V-02
recorded). Nothing else changes: no header on error responses, no preflight (`OPTIONS` keeps its current
405 / `Allow` behaviour), no `Access-Control-Allow-Credentials`, no other route. If V-02 recorded a value
other than `*` (e.g. an echoed origin), stop and return CONTRACT_ISSUE.

## Acceptance criteria (each becomes a test, in this order; running `Simulator` as in INC-1 `test_issuer.py`)
1. Given a GET of the discovery URL with `Origin: http://127.0.0.1:5555`, then 200 with
   `Access-Control-Allow-Origin` equal to the V-02 value and the body unchanged.
2. Given a GET of the JWKS URL, then the same header.
3. Given a 404 path, a 405 method and an oversized request head, then no `Access-Control-*` header.
4. Given any response, then `Access-Control-Allow-Credentials` is absent.
5. Given INC-1 `test_issuer.py` and `test_simulator.py`, then they stay green.

## Security requirements
- SR-13 / NFR-6: the simulator's behaviour matches production (no relaxed or extra header); development
  anchors are unchanged.

## Constraints
- No new dependencies. Do not touch the launcher, token minting or state handling.
