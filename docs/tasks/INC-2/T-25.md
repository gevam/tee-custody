## Interface contract
INC-2-API §5.3 verbatim:
```python
def generate_channel_suite(out_dir: Path, *, now: int | None = None) -> Path: ...   # writes out_dir/channel/suite.cbor
```
> It uses freshly generated keys from `os.urandom` and a fresh simulator issuer, never the state dir. Sealing
> uses `pyhpke` directly. Ephemeral-key injection (`eks`) is permitted here and in tests only (ADR 0011 C5). The
> output covers the named cases of §3.2. `teecustody-sim vectors --out DIR [--force]` additionally writes
> `DIR/channel/suite.cbor` and prints three paths in the order attestation, corpus, channel. `OUTPUT_EXISTS`
> covers all three files.

Construction rules (fixed): suite shape = `spec/wire/channel-vectors.cddl` and the `spec/vectors/README.md`
channel format section (T-03), including the `plaintext` rules, `layout-case.inputs` keys and the case-id
rules (`c2t_`/`t2c_` frame prefixes, `<kind>_accept` / `<kind>_<field>_range` layout ids). Tokens: own
`SimKeys`, `TokenMinter`, and `build_trust_profile(jwks_uri="http://127.0.0.1:8792/jwks", ...)` (v2, INC-2-API
§16.3). The `http` map is exactly `{"http://127.0.0.1:8792/jwks": <issuer JWKS bytes>}`: no discovery URL and no
attacker entry (§5.3, §16.4). The rest uses this module's own constants (launch config, audience);
`token_dbgstat_enabled` via `parse_alteration("dbgstat=enabled")`. IK is a raw `cryptography` Ed25519 key
(not `IdentityKey`); pre-key signatures use the §2 layout via `teecustody.channel.codec.prekey_signing_message`;
alternative-digest/instance cases sign the alternative message. Well-formed bundles use `codec.encode_bundle`;
malformed ones use `teecustody.wire.encode` on raw dicts; `noncanonical` is one canonical bundle with its first
integer argument re-encoded non-shortest. AEAD uses `cryptography` `AESGCM` with this module's own nonce
builder (`b"\x00" * 4 + seq.to_bytes(8, "big")`). `pre-key ttl` = 3600 s; expired entries have `not_after =
now − 10`. `info_other_prekey` seals with `hpke_info(ik_pub, prekey_id + 1)`. Schema-valid AAD mutations (T-03 Low, accepted):
- `opens/aad_modified` replaces one hex character of the AAD `client_id` with a different lowercase hex
  character, so it still matches `[0-9a-f]{32}`. The envelope is re-encoded canonically, and `enc`/`ct` are
  unchanged. Expected: `reject` / `OPEN_FAILED` (c2t only; opens have no t2c direction).
- `frames/c2t_aad_op_modified` and `frames/t2c_aad_op_modified` change the frame AAD `op` from the valid case's
  op to a different string matching `[a-z][a-z0-9_.]{0,63}`. If the op ends in a lowercase letter, that letter
  becomes the next one (`z`→`a`), so `test.echo` becomes `test.echp`. Otherwise `a` replaces the last character. The envelope is re-encoded canonically, and the ciphertext is unchanged. Expected: `reject` /
  `AUTH_FAILED` in both directions. The suite holds only synthetic
keys and the public trust profile. `cli.py`: add the channel path constant, include it in `_check_vectors_out`,
the existence check, staging and output list; before the first `os.replace`, verify every target directory is
writable (`os.access(dir, os.W_OK)`), else `SimConfigError(INVALID_PATH)` with nothing replaced (BACKLOG B-23).

## Acceptance criteria (each becomes a test, in this order)
1. Given `generate_channel_suite(tmp, now=N)`, then the file decodes with `CHANNEL_SUITE_LIMITS` to a map with
   exactly the CDDL keys, `proto == PROTO`, `verify_at_ms == N * 1000`.
2. Given the suite, then each array contains exactly the §3.2 named case ids (transcribed in the test), each once,
   plus one layout accept case per builder and one reject per §2 width/range rule.
3. Given each `bundle-case`, then `expect`/`error_code`/`usable_prekey_ids` are consistent (accept iff
   `error_code == "none"`; ids sorted; empty iff reject) and the valid bundle's signatures verify with the
   test's own Ed25519 check over the §2 preimage.
4. Given each `open-case` with `expect == "accept"`, then a `pyhpke` recipient in the test opens it with the given
   key and its exports equal `sk_c2t`/`sk_t2c`; each reject case fails as its `error_code` says.
5. Given each `frame-case` and `result-case`, then the test's own AES-GCM decrypt agrees with `expect`, `plaintext`
   and the `plaintext` nil/non-nil rule.
6. Given two runs, then all keys differ between runs and no PEM/`PRIVATE KEY` text appears; the state dir is
   never created (run with `HOME` and cwd in `tmp_path`).
7. Given `teecustody-sim vectors --out DIR`, then stdout is exactly the attestation, corpus and channel paths;
   with any of the three existing and no `--force` → `OUTPUT_EXISTS` and nothing written; `--force` replaces all.
8. Given a read-only `DIR/channel`, then `INVALID_PATH` and the attestation and corpus files are unchanged.
9. Given the suite, then `profile_json` parses as a v2 development profile whose `jwks_uri` is the only `http`
   key, and no `http` key ends in `/.well-known/openid-configuration`.
10. Given `aad_modified`, `c2t_aad_op_modified` and `t2c_aad_op_modified`, then each decodes against its CDDL
    (schema-valid). Their outcomes are `OPEN_FAILED`, `AUTH_FAILED` and `AUTH_FAILED`, confirmed by the
    test's own `pyhpke`/`AESGCM` open.
11. Given `importlib.metadata.requires("teecustody-sim")`, then it is exactly `cryptography==50.0.2`,
    `pyhpke==0.6.5` and `teecustody==0.1.0`.
