## Goal

WebAuthn PRF vault included, and every unsupported browser capability fails closed as FACTS.md records.

## Interface contract
INC-2-API §9.3 **revision 3** verbatim (the D-043 `connect-src`, the 2026-10-12 `img-src 'self'` / favicon ruling,
steps B1–B3 and the Firefox vault expectations). Normative extracts:
> `serve.mjs`: `node:http` static server on 127.0.0.1:0. It serves `index.html` (one `<script src="/harness.js"
> integrity="sha384-…" crossorigin="anonymous">`, nothing inline, no `<link rel="icon">`), `harness.js`
> (esbuild bundle of `test/browser/harness/index.ts`) and `GET /favicon.ico` (fixed `204 No Content`, no body),
> with header `Content-Security-Policy: default-src 'none'; script-src 'sha384-<harness.js>'; connect-src
> <gateway origin> <jwks origin>; img-src 'self'; style-src 'none'; base-uri 'none'; form-action 'none';
> frame-ancestors 'none'; object-src 'none'` (enforce mode, no `'self'` or unsafe keyword **in `script-src`**).
> No violation filter is allowed. Every `securitypolicyviolation` event counts in every browser.
> `<jwks origin>` is `new URL(profile.jwks_uri).origin`. It is never a discovery origin. Under the simulator it
> equals the issuer's HTTP origin.
> `discovery_cors`: a page `fetch` of the simulator discovery URL must reject because of CORS (`"blocked"`), while
> `attestation` is `"ok"`. `attacker`: `verifyAttestation` of `fixture.attacker_token` gives `UNTRUSTED_SIGNER`
> (`"rejected"`), while a page `fetch` of `fixture.attacker_jwks_url` succeeds. `pin_canonical`: the Google
> `jwks_uri` constant survives `new URL(...).href` unchanged. `window.__result = { violations: number, steps:
> Record<string, "ok" | "blocked" | "rejected" | CapabilityErrorCode | ChannelErrorCode | AttestationErrorCode> }`.
> Vault outside Chromium, unless PRF is available: WebKit `UNSUPPORTED`; Firefox `UNSUPPORTED`, or
> `USER_PRESENCE_REQUIRED` when the ceremony waits until `timeoutMs` (3000 for Firefox). The `shares` store is
> empty afterwards in every case.

Decisions:
- `global-setup.ts` starts `serve.mjs` first, so the port is known. It then starts the e2e harness with
  `--cors-origin <serve origin>` (TL-8) and reads the ready line.
- It then has `serve.mjs` bundle `harness.js`, injecting the gateway origin, the profile JSON and the
  `fixture.json` values (TL-8, including `discovery_url`, `attacker_jwks_url` and `attacker_token`) through
  esbuild `define`. There is no inline script, and no same-origin fetch, which `connect-src` would block.
- `serve.mjs` computes the `sha384` of the exact `harness.js` bytes it serves.
- Step names, in order: `crypto`, `fetcher`, `attestation`, `transport`, `channel`, `vault`, `discovery_cors`,
  `attacker`, `pin_canonical`.
- The `attestation` step is `verifyBundle` of the first bundle from `FetchTransport.getBundles()`, using
  `FetchFetcher` and the profile, → `"ok"`.
- `pin_canonical` reads the constant through a parsed production profile literal, built in the harness from the
  §16.1 production shape (inert anchors). Core exports no constant.
- The expected per-browser step values come from FACTS.md's support matrix and are written as a table in
  `csp.spec.ts`.

Vault in Chromium (A2, INC-2-API §8.4 option (b)):
- The first `vault.set` performs two WebAuthn ceremonies, `create` (`prf: {}`) and then one `get`, both against
  the CDP virtual authenticator.
- The harness then runs `vault.get` and checks that the round trip returns the same 32 bytes.
- The step stays `ok` only if the bytes match.

## Acceptance criteria (each becomes a test, in this order)
1. Given Chromium with the PRF authenticator, then `discovery_cors` is `"blocked"`, `attacker` is `"rejected"`
   (B1, B2), every other step is `ok` (B3 included), and `violations === 0`.
2. Given Firefox and WebKit, then each crypto, fetcher, attestation, transport and channel step equals the
   FACTS.md matrix value (`ok` or a fail-closed code). The vault step follows the Firefox/WebKit rule above, and
   the `shares` store is empty. `discovery_cors` is `"blocked"`, `attacker` is `"rejected"`, `pin_canonical` is
   `ok`, and `violations === 0`.
3. Given the positive-control page under the same CSP header, then `violations ≥ 1`.
4. Given Chromium with `hasPrf: false`, then `vault` step `UNSUPPORTED` and the `shares` store is empty
   (read through `page.evaluate` on IndexedDB).
5. Given the served `index.html`, then it contains exactly one `<script>` element with `integrity`, `crossorigin`
   and `src`, no inline script or handler and no `<link rel="icon">`. The `Content-Security-Policy` response
   header equals, byte for byte, the §9.3 string with the gateway origin, the JWKS origin and the served
   `harness.js` hash substituted. `script-src` contains no `'self'`, `'unsafe-inline'`, `'unsafe-eval'` or
   `'strict-dynamic'`.
6. Given `GET /favicon.ico`, then status 204 with an empty body. Given Firefox loading `index.html`, then no
   `img-src` violation is recorded.

## Security requirements
- SR-1 / T-29: criteria 1–2 (B1, B2). SR-13: criteria 1–6 are REQUIREMENTS SR-13's library harness ("a headless-browser harness runs vault and
  transport under the strict CSP with zero violations", ADR 0008). Never relax the CSP to make a step pass; a
  failure is a defect or CONTRACT_ISSUE.
