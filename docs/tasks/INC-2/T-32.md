# T-32: Run vault, transport and channel in real browsers under the strict CSP (Playwright harness)

Increment: INC-2   Wave: 5   Tier: STRONG (SR-13 control; security.paths: Web)   Depends on: T-31, T-17, T-18, T-19, T-20, T-26, V-02 (and T-21 per CI-2-1)

## Goal
The libraries are proven to run under an enforce-mode, hash-only CSP with zero violations in the CI browsers,
WebAuthn PRF vault included, and every unsupported browser capability fails closed as FACTS.md records.

## Owned files
- `packages/teecustody-web/test/browser/{serve.mjs,csp.spec.ts,global-setup.ts}` (create)

- `packages/teecustody-web/test/browser/control/inline.html` (create: positive control)

## Interface contract
INC-2-API §9.3 verbatim:
> `serve.mjs`: `node:http` static server on 127.0.0.1:0. It serves `index.html` (one `<script src="/harness.js"
> integrity="sha384-…" crossorigin="anonymous">`, nothing inline) and `harness.js` (esbuild bundle of
> `test/browser/harness/index.ts`), with header `Content-Security-Policy: default-src 'none'; script-src
> 'sha384-<harness.js>'; connect-src <gateway origin> <issuer origin>; img-src 'none'; style-src 'none'; base-uri
> 'none'; form-action 'none'; frame-ancestors 'none'; object-src 'none'` (enforce mode, no `'self'`, no unsafe
> keywords).
> `harness/index.ts` registers a `securitypolicyviolation` listener first, then runs: `createWebCrypto` (HPKE seal,
> Ed25519 verify), `FetchFetcher` against the simulator issuer, `FetchTransport` + `ChannelClient` against the e2e
> harness (open → `test.echo` → close), and `PrfShareVault` set/get/clear. It exposes `window.__result = {
> violations: number, steps: Record<string, "ok" | CapabilityErrorCode | ChannelErrorCode> }`.
> `csp.spec.ts`: Chromium with a CDP virtual authenticator (`hasPrf: true`, `hasUserVerification: true`,
> `isUserVerified: true`) — every step `ok`, `violations === 0`. Firefox and WebKit — crypto, fetcher, transport and
> channel steps `ok` or a recorded fail-closed `UNSUPPORTED`/`CRYPTO_UNAVAILABLE` (V-2.2, V-2.4), vault
> `UNSUPPORTED` unless PRF is available, `violations === 0`. A positive-control page with one inline script must
> report ≥ 1 violation. A PRF-less virtual authenticator (`hasPrf: false`) must give `vault.set` → `UNSUPPORTED`
> and an empty `shares` store.

Decisions: `global-setup.ts` starts `serve.mjs` first (port known), then the e2e harness with
`--cors-origin <serve origin>` (TL-8), reads the ready line, then has `serve.mjs` bundle `harness.js` with the
gateway origin, profile JSON and `fixture.json` values injected through esbuild `define` (no inline script, no
same-origin fetch, which `connect-src` would block). `serve.mjs` computes the `sha384` of the exact `harness.js`
bytes it serves. Step names: `crypto`, `fetcher`, `transport`, `channel`, `vault`. Expected per-browser step
values are read from FACTS.md's support matrix and written as a table in `csp.spec.ts`.

## Acceptance criteria (each becomes a test, in this order)
1. Given Chromium with the PRF authenticator, then all five steps are `ok` and `violations === 0`.
2. Given Firefox and WebKit, then each step equals the FACTS.md matrix value (`ok` or a fail-closed code) and
   `violations === 0`.
3. Given the positive-control page under the same CSP header, then `violations ≥ 1`.
4. Given Chromium with `hasPrf: false`, then `vault` step `UNSUPPORTED` and the `shares` store is empty
   (read through `page.evaluate` on IndexedDB).
5. Given the served `index.html`, then it contains exactly one `<script>` element with `integrity`, `crossorigin`
   and `src`, no inline script or handler, and the CSP header contains no `'self'`, `'unsafe-inline'`,
   `'unsafe-eval'` or `'strict-dynamic'`.

## Security requirements
- SR-13: criteria 1–5 are REQUIREMENTS SR-13's library harness ("a headless-browser harness runs vault and
  transport under the strict CSP with zero violations", ADR 0008). Never relax the CSP to make a step pass; a
  failure is a defect or CONTRACT_ISSUE.
