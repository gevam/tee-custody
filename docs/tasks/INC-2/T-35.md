## Goal
A host's production build fails unless Google's live discovery document binds the profile's `issuer` and
`jwks_uri` exactly. A scheduled CI job repeats this check against Google with a CORS probe and no secrets.

## Acceptance criteria (each becomes a test, in this order; INC-2-API §16.9 D1–D4)
1. (D1) Given fixture Fetchers, then each `DiscoveryBindingErrorCode` is produced. This includes the
   exact-string mismatches: a discovery `jwks_uri` with a trailing `/`, an upper-case host or `%40`, and an
   `issuer` with a trailing `/`. The fetch order is discovery then JWKS, with count 2. A production profile with
   a non-Google discovery URL → `INVALID_ARGUMENT` before any fetch. Zero usable keys → `JWKS_INVALID`.
2. (D2) Given `main`, then each §16.5 table row gives its exit code and one stderr line. The success line is
   exact. `NODE_TLS_REJECT_UNAUTHORIZED=0` (`vi.stubEnv`) → exit 2 with zero `fetch` calls. The CORS probe runs
   against local `node:http` servers with and without ACAO (`absent`, `invalid`, value).
3. (D3) Given `ci.yml` (line-based), then the job exists, its `if` is exactly the §16.6 expression, it
   contains no `secrets.`, and its run lines equal §16.6 steps 2 and 3.
4. (D4) Given the web `lint` scan, then it still exits 0 with `src/profile/**` present, and its metafile has no
   `src/profile/` input (T-27 rule `profile-input`).
5. Given `uvx semgrep==1.178.0 --test .semgrep/`, then both rules hold their fixtures:
   - `"INSECURE_TLS_ENVIRONMENT"` is `ok`;
   - `insecure`, `allowInsecure` and `ALLOW_INSECURE_TLS_ENVIRONMENT` fire;
   - the refusal comparison is `ok`;
   - the assignment, `delete`, `!==` and bracket forms fire, and so does `rejectUnauthorized: false`.
6. Given `tests/integration/contracts/test_profile_cli_contract.py`, then it is green.
