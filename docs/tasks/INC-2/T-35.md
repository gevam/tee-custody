> **Amendment A3 (2026-10-15, Tech Lead; round-1 review of 0bed446: Code Review Medium and Security Review Low R1,

> **(R1) Every unexpected error fails closed.** `main` returns only 0, 1 or 2. No caught value in `cli.ts` is
> narrowed with `as`; every catch tests with `instanceof`.
> - Probe step: any throw while a probe is issued, including a synchronous throw from `request` (for example
>   `ERR_INVALID_PROTOCOL`), is a probe transport failure, and `probe` resolves `null`. For the JWKS probe that gives
>   `CORS_MISSING`, exit 1. The discovery probe is still informational: exit 0, with the value that the round-2 Low
>   fix assigns to a failed probe.
> - Binding step: `bind` maps a caught value to its code only when it is `instanceof DiscoveryBindingError`. Any
>   other value propagates.
> - `main` keeps the code and exit of a caught value only when it is `instanceof CliFailure`. Any other value
>   writes exactly the stderr line `INTERNAL`, writes nothing to stdout and returns 1. The error's message, name and
>   stack are never written (SR-11). `INTERNAL` is a CLI-only code and is not added to `DiscoveryBindingErrorCode`.
>   The precedent is §8.3 (FetchTransport: "anything else → `INTERNAL`").
> - Library: in steps 2 and 5, "the call rejects" includes a synchronous throw from `fetcher.get`. This already
>   holds on 0bed446; criterion 8d pins it.
>
> **(R2) Option (b): the Fetcher's size rejection maps to `*_INVALID`.** `FetchFetcher` (§8.2 step 5) rejects with
> `CapabilityError("INVALID_RESPONSE")` in exactly three cases: a declared `Content-Length` that is malformed, one
> above `maxBodyBytes`, or a streamed body above `maxBodyBytes`. Its other rejections are `INVALID_ARGUMENT`,
> `UNAVAILABLE` and `HTTP_ERROR`. The CLI sees only `DiscoveryBindingError`, so the mapping lives in
> `discovery-binding.ts`. In steps 2 and 5, a rejection that is `instanceof CapabilityError` (a value import from
> `@teecustody/core`; it is not a Node import) and has `code === "INVALID_RESPONSE"` gives `DISCOVERY_INVALID` or
> `JWKS_INVALID`. Every other rejection or throw gives `*_UNAVAILABLE`. That includes a plain object
> `{ code: "INVALID_RESPONSE" }` that is not a `CapabilityError`. The in-function `maxDocumentBytes` check stays,
> because it governs Fetchers with a larger cap. `cli.ts` needs no change for R2. If undici itself rejects a
> malformed `Content-Length` before `FetchFetcher` sees it, that is a network failure (`*_UNAVAILABLE`). This is
> correct and is not tested at CLI level.

## Goal
A host's production build fails unless Google's live discovery document binds the profile's `issuer` and
`jwks_uri` exactly. A scheduled CI job repeats this check against Google with a CORS probe and no secrets.

   exact-string mismatches: a discovery `jwks_uri` with a trailing `/`, an upper-case host or `%40`, and an
   `issuer` with a trailing `/`. The fetch order is discovery then JWKS, with count 2. A production profile with
   a non-Google discovery URL → `INVALID_ARGUMENT` before any fetch. Zero usable keys → `JWKS_INVALID`.
2. (D2) Given `main`, then each §16.5 table row gives its exit code and one stderr line. The success line is
   exact. `NODE_TLS_REJECT_UNAUTHORIZED=0` (`vi.stubEnv`) → exit 2 with zero `fetch` calls. The CORS probe runs

   contains no `secrets.`, and its run lines equal §16.6 steps 2 and 3.

   `src/profile/` input (T-27 rule `profile-input`).
