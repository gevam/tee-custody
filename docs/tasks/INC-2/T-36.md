## Acceptance criteria (each becomes an acceptance test, in this order)
1. (SR-1) Given a valid token and a recording Fetcher, then verification succeeds after exactly one fetch of
   `profile.jwks_uri`, and no fetch names `openid-configuration`.
2. (SR-1, T-29) Given a token signed by the attacker key (own `kid`, and the issuer's `kid`) while the attacker
   JWKS is served on the same origin, then `signature` / `UNTRUSTED_SIGNER`.
3. (SR-1) Given an INC-1 v1 profile, or a v2 profile carrying `discovery_url` or `jwks_origin`, then
   `INVALID_PROFILE`. Given a production `jwks_uri` with a trailing `/`, an upper-case host or `%40`, then
   `INVALID_PROFILE` at `jwks_uri`.
4. (FR-3) Given the live simulator, then `teecustody-sim profile` emits a v2 profile that Core parses.
   Discovery has no `Access-Control-Allow-Origin`, and `/jwks` has one.
5. (FR-3) Given the simulator CLI, then `token --case jwks_other_path` and `--case jwks_other_path_same_kid`
   produce tokens that Core rejects at `signature`. The FR-3 negative-case table gains rows 38–39.
6. (FR-2) Given network failure on the JWKS URL, then the verifier fails closed (`UNTRUSTED_SIGNER`). The old
   "discovery/JWKS cannot be fetched" case becomes JWKS-only.
7. Given every edited file, then no v1 profile literal remains except as a rejection input.
