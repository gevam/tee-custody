## Goal
A connection that never finishes its request headers is closed after `header_read_timeout_s`. Open connections are capped at `max_connections`, so a slow-header flood cannot exhaust descriptors. A request the HTTP parser rejects gets the documented `{"code":"INVALID_ARGUMENT"}` body. ASGI middleware cannot do any of this: uvicorn 0.54.0's h11 protocol arms no timer before the first request, cancels its keep-alive timer on any byte, and answers parse failures in `send_400_response` before the app runs. Measured: 51/51 partial and idle connections were still open after 25 s; parse failures returned `text/plain` `Invalid HTTP request received.`. A scratch prototype of the design below closed all 51 in 3 s and returned the exact JSON 400. No uvicorn option bounds header time (`timeout_keep_alive` applies only after a response; `h11_max_incomplete_event_size` bounds bytes, not time). A fronting-proxy rule alone is rejected because it would leave the reference gateway's own run paths (dev, harness, CI) unbounded.

## Interface contract: INC-2-API §6 "Server hardening" (the original proposal is below; the committed §6 text, with A1 changes (1)–(3), governs)
> **Server hardening (2026-10-15; QA D-03, D-04; SR-4, T-07, FR-5).** Appended to `GatewayLimits`, kw_only:
> ```python
>     header_read_timeout_s: float = 10.0    # 1.0..60.0, finite; total deadline for one request's header block
>     max_connections: int = 512             # >= max_concurrency; open connections per process, any state
> ```
> ```python
> # notes_gateway/server.py (not re-exported from notes_gateway)
> def uvicorn_config(app: fastapi.FastAPI, *, limits: GatewayLimits = GatewayLimits(),
>                    host: str, port: int) -> uvicorn.Config: ...
> ```
> - `uvicorn_config` validates `limits` as `create_app` does. It returns a `uvicorn.Config` with `http` set to the gateway's h11 protocol class (never `"auto"` or httptools), `proxy_headers=False`, `server_header=False`, `access_log=False`, `h11_max_incomplete_event_size=16384`, `timeout_keep_alive=5` and `log_level="warning"`. It never sets `forwarded_allow_ips` or `limit_concurrency`. Pass it the same `limits` given to `create_app`. Every place in this repository that runs the gateway uses it (`dev.py`, `tests/e2e/channel_harness.py`). This replaces the "Server configuration" bullet's list of settings; its test still holds.
> - **Header-read deadline.** The complete header block of each request must arrive within `header_read_timeout_s`. The clock starts when the connection is accepted and, on a kept-alive connection, when the previous response completes. It is a total deadline, not reset by data. On expiry the connection is closed and no bytes are written. Once the headers are complete, only the body deadline and the route apply.
> - **Connection cap.** An accepted connection that would exceed `max_connections` open connections is closed at once, and no bytes are written. Other connections are unaffected.
> - **Parse failures.** A request the HTTP parser rejects is answered with exactly these bytes, and the connection is then closed. Examples are a header block over 16384 bytes, a malformed header, a missing `Host` and non-HTTP bytes.
>   `HTTP/1.1 400 Bad Request\r\ncontent-type: application/json\r\ncontent-length: 27\r\ncache-control: no-store\r\nx-content-type-options: nosniff\r\nconnection: close\r\n\r\n{"code":"INVALID_ARGUMENT"}`
>   No request was parsed, so the response carries no CORS headers.
> - Logs (outcome only, no fields): `GATEWAY_HEADER_TIMEOUT`, `GATEWAY_CONNECTION_LIMIT`, and `GATEWAY_INVALID_ARGUMENT` for a parse failure.
> - Validation: `header_read_timeout_s` must be a finite `int`/`float` in 1.0..60.0, with `bool` refused. `max_connections` must be an `int` ≥ `max_concurrency`, with `bool` refused. Anything else → `ValueError("INVALID_LIMITS")`.

Fixed decisions (`server.py`):
- A private factory `_protocol_class(limits) -> type[H11Protocol]` returns a subclass of `uvicorn.protocols.http.h11_impl.H11Protocol`.
- Overrides:
  - `connection_made`: call `super()`. Then, if `len(self.connections) > max_connections`, close the transport, log, and return. Otherwise arm the deadline.
  - `on_response_complete`: arm the deadline if the transport is not closing, then call `super()`. Arming must come first, because `super()` may parse a pipelined request.
  - `connection_lost`: cancel the handle, then call `super()`.
  - `send_400_response(msg)`: if `self.cycle` is not `None` and `self.cycle.response_started and not
    self.cycle.response_complete`, write nothing. Otherwise write the constant. In both cases close the transport
    and log `GATEWAY_INVALID_ARGUMENT`. Ignore `msg` (A1 (2)).
- Arming: cancel any pending handle, then `self.loop.call_later(header_read_timeout_s, expire, self.cycle)`. `expire` closes the connection only if `self.cycle` is still the object recorded when arming, and the transport is not closing. A new request creates a new cycle.
- Call `uvicorn.Config` through the module attribute (`import uvicorn`), so the existing recorders in `test_dev.py` and `test_channel_e2e.py` keep working. The logger is `teecustody.obs.get_logger("gateway")`.

## Acceptance criteria
Tests run against a live `uvicorn.Server(uvicorn_config(create_app(fake), limits=…, host="127.0.0.1", port=0))` in a thread, using raw sockets, bounded waits and teardown. A fake loop or transport (via `_loop=`) is allowed only for criterion 11.
1. Given `header_read_timeout_s=1.0`, when a client sends `GET /bundles HTTP/1.1\r\nHost: x\r\nX-A: ` and stops, then the connection reaches EOF with zero bytes in 0.9–3.0 s, there are 0 queue calls, and exactly one `GATEWAY_HEADER_TIMEOUT` is logged.
2. Given the same limits, an idle connection that sends nothing is closed with zero bytes in 0.9–3.0 s.
3. Given the same limits, one header byte every 0.25 s is still closed by 3.0 s. The deadline is total.
4. Given the same limits, after a `200` on a kept-alive connection, a second request trickled byte by byte is closed by 3.0 s after the response.
5. Given `header_read_timeout_s=1.0` and `body_read_timeout_s=3.0`, a POST declaring 10 bytes and sending 1 receives the exact `408 {"code":"REQUEST_TIMEOUT"}` at 2.5–5.0 s, never a close near 1 s. A relay whose `list_bundles` sleeps 2 s still answers `200`.
6. Two pipelined GETs in one write both get `200`.
7. Given `max_concurrency=4`, `per_source_max_in_flight=4`, `max_connections=4` and `header_read_timeout_s=10.0`:
   - with 4 idle connections open, a 5th is closed with zero bytes within 0.5 s, and `GATEWAY_CONNECTION_LIMIT` is logged once;
   - after one held connection closes, a new connection gets `200`.
