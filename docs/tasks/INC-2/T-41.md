## Goal
`packages/teecustody-core/test/channel/session.test.ts`, test "criterion 7: Session.request > refuses more than maxInFlight pending requests without consuming a seq" (lines 186–198 at 31bae29) ends with `expect(workload.frames.map((f) => f.seq)).toEqual([0, 1, 2])`. It failed 1 run in 8 with `[1, 0, 2]`:
- `seq` is allocated synchronously, but encryption finishes asynchronously, so concurrent requests post in completion order.
- §7.4 promises distinct, monotonically allocated seqs. It does not promise post order (T-31 A4, D-062, B-26).

So the test over-asserts. When this task is done, the test asserts only what §7.4 promises, and a second test forces the reorder.

## Interface contract (consumed; INC-2-API §7.4, verbatim)
```
- The one private sealing method `#sealNext(op, payloadBytes)` reads `seq = nextC2tSeq` and **assigns
  `nextC2tSeq = seq + 1` synchronously, before its first `await`**. It then builds the frame AAD and calls
  `aes256GcmEncrypt`. Concurrent `request()` calls therefore always get distinct `seq`s.
- Nothing ever decrements, resets or restores `nextC2tSeq`: ...
- More than `maxInFlight` pending → `INVALID_ARGUMENT`.
```
