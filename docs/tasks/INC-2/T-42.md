## Goal
A host using the default gateway and the default `FetchTransport` can always collect a full response page. Today `maxResponseBytes` is required, and every call site passes the documented 1 MiB. A full page of maximal frames is 1,406,937 B, so a busy client's poll fails with `INVALID_RESPONSE` on every attempt and its cursor never advances (D-07). After this task the option is optional, and an omitted option means 2,097,152.

## Interface contract
INC-2-API §8.3, as committed:
```ts
export interface FetchTransportOptions {
    readonly baseUrl: string;             // https origin (+ optional path prefix); http only on loopback hosts
    readonly maxResponseBytes?: number;   // default 2097152 (D-07: ≥ the §6 maximal page at default limits)
    readonly timeoutMs: number;
    readonly fetch?: FetchFn;
}
```
> The option is optional. When it is omitted or `undefined`, the limit is 2,097,152 bytes. … A value that is given must still be a positive safe integer; anything else, including `null`, is `TypeError("INVALID_CONFIG")` as before. … The default is not exported as a constant: the number is the contract.

Decision: test `options.maxResponseBytes === undefined` (`in` is not used). The `undefined` → default rule applies to this option only. `timeoutMs` stays required.

## Acceptance criteria
Each criterion is a vitest test, seen failing first. Build pages with a test helper that emits valid compact §6 JSON of an exact byte length. Pad the length with the `next` cursor (1..128 characters) and the last item's base64url length. Never use a base64url length ≡ 1 (mod 4).
1. Given `maxResponseBytes` omitted, a streamed `GET /responses` body (no `Content-Length`) of exactly 2,097,152 B resolves. A body of 2,097,153 B is `INVALID_RESPONSE`, and the stream is cancelled. A `Content-Length: 2097153` response is `INVALID_RESPONSE` before any read, and the body reader is never acquired. First red: today, construction throws `INVALID_CONFIG`.
2. Given the default, a `GET /responses` page of exactly 1,406,937 B resolves to 32 responses with `next` equal to the 128-character cursor. The page has 32 items, each `body` the base64url of 32,926 bytes, and `"next":"A"×128`; assert its length first. A `GET /bundles` page of exactly 1,399,133 B (16 × 65,536-byte bundles) resolves to 16 bundles. First red: as in criterion 1.
3. Given `{ maxResponseBytes: undefined }`, behaviour is identical to criterion 1. First red: today `INVALID_CONFIG`.
4. Explicit values still apply:
   - `4096` accepts 4,096 B and refuses 4,097 B (the existing tests stay unchanged);
   - an explicit `1_048_576` refuses the criterion-2 1,406,937 B page with `INVALID_RESPONSE`, as §6's interoperability rule implies;
   - an explicit `3_000_000` accepts a 2,500,000 B page.
5. Validation is unchanged for given values. Each of `0, -1, 1.5, NaN, Infinity, 2**53, "1024", null` → `TypeError("INVALID_CONFIG")`, and `timeoutMs` omitted → `INVALID_CONFIG`. These are guards, already green: show `null` first-red with a local `?? DEFAULT` mutation.
6. API surface:
